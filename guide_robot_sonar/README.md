# guide_robot_sonar

Пакет опроса ультразвуковых дальномеров (sonar dome) робота Guide-Robot и публикации
`sensor_msgs/Range` для `nav2_collision_monitor`. Смешанный C++/Python: низкоуровневый
драйвер UART собран как pybind11-модуль `furo_sonars_cpp`, поверх него — два
альтернативных rclpy-узла.

## Обзор

Состав пакета:

- `include/guide_robot_sonar/sonar_driver.hpp`, `src/sonar_driver.cpp` — драйвер
  на C++: открывает serial-порт, циклически опрашивает 7 датчиков по одному
  общему UART, хранит в потокобезопасной карте последнее `SonarReading` на
  датчик — дальность, счётчик подряд идущих неудачных опросов, номер опроса
  и возраст показания.
- `src/sonar_driver_bindings.cpp` — pybind11-обёртка, экспортирует класс
  `SonarDriver` в Python как модуль `furo_sonars_cpp`.
- `scripts/sonar_node_mult.py` — **боевой** узел: публикует по одному
  `sensor_msgs/Range` на датчик в `sonar/range/<frame_id>` с `SensorDataQoS`
  (`BEST_EFFORT`), рассчитан на прямое подключение к `nav2_collision_monitor`.
  Запускается из `guide_robot_bringup/launch/hardware.launch.py:174-186`
  (`executable="sonar_node_mult.py"`, включён по умолчанию, `launch_sonar:=true`).
- `scripts/sonar_node.py` — более старый/альтернативный узел: публикует
  агрегированное сообщение `guide_robot_msgs/SonarRanges` в `sonar/ranges`,
  опционально по одному `Range` на датчик в `sonar/<frame_id>` (другой префикс,
  не совпадает с `sonar/range/<frame_id>`!), плюс `MarkerArray` для RViz/Foxglove.
  Ни одним launch-файлом сейчас не запускается.
- Сообщение `guide_robot_msgs/SonarRanges` (`std_msgs/Header header` +
  `sensor_msgs/Range[] ranges`) объявлено в `guide_robot_msgs`, но реально
  потребляется только тестовым/симуляционным кодом (`sonar_merge.py` в
  `guide_robot_simulation`), не production-путём collision avoidance.

Логика фильтрации (медиана → deadband → гистерезис у границы диапазона)
**идентична и продублирована** в обоих узлах (`sonar_node.py:62-112` и
`sonar_node_mult.py:70-123`) — отдельного «фильтр-ноды» в пакете нет, вся
фильтрация встроена в publish-callback.

## Аппаратный интерфейс

- Единая последовательная шина (UART/USB-serial, по умолчанию порт
  `/dev/tty_sonar`, 9600 бод) на 7 физических датчиков, ID `{0,3,1,4,2,5,6}`
  (`sonar_driver.hpp:92`).
- Протокол poll/response: команда `0xCC, 0x30+id, checksum` →
  ответ 5 байт `0xCC, id?, distLo, distHi, xor-checksum`
  (`sonar_driver.cpp:244-276`, XOR по первым четырём байтам). Байт с
  идентификатором **не сверяется** — валидируются только заголовок `0xCC` и
  контрольная сумма, поэтому опоздавший кадр от предыдущего датчика в
  принципе может быть засчитан текущему. Отсюда выдержка после каждого
  опроса, который реально пингнул (см. п. 4).
- Перед стартом опроса один раз посылается «пробуждение купола»
  `activate_dome()` — фиксированная пауза 500 мс. Подтверждения в протоколе
  нет, проверяется только полная запись в порт (`is_dome_active()`).
- Отображение `sonar_id → URDF frame_id` (`sonar_sensor_1/2/4/5/6/8/9`)
  задаётся словарём `SONAR_MAPPING` в `scripts/sonar_mapping.py` — общий
  источник правды для обоих узлов, сверен с
  `guide_robot_description/urdf/guide_robot.urdf.xacro:171-180`.
- Сырые показания — это **не миллиметры**, а счётчик времени пролёта эха;
  переводятся в метры параметрами `range_scale`/`range_offset`
  (`sonar_node_mult.py:150-151`, `range_scale=0.0026104`, `range_offset=-0.01303`).
- Значения `range` в `SonarReading`: `0xFFFF` — эха нет, `-1` — запрос ушёл,
  но ответ не пришёл или битый, `-2` — запрос не удалось отправить (порт
  пропал). Для узла `-1` и `-2` одинаково ошибка, различается только пауза
  перед следующим датчиком.
- QoS: `sonar_node_mult.py:62-67` использует `SensorDataQoS`
  (`BEST_EFFORT`, `depth=1`) намеренно, чтобы совпасть с
  `rclcpp::SensorDataQoS()` подписчика `nav2_collision_monitor`; в коде есть
  явный комментарий «Do not change to RELIABLE». `sonar_node.py`, напротив,
  создаёт публикаторы с QoS по умолчанию (`RELIABLE`, глубина 10) —
  `sonar_node.py:190,195-198`.
- Топики и `frame_id` сверены с конфигом Nav2:
  `guide_robot_navigation/generated_config/first_iter_nav2.yaml:591-624`
  подписывается на `/sonar/range/sonar_sensor_{1,9,2,8,4,6,5}` — совпадает с
  тем, что публикует `sonar_node_mult.py` (топик-префикс по умолчанию
  `sonar/range`). `sonar_node.py` публикует в другой неймспейс (`sonar/<frame>`)
  и с несовместимым QoS — если его когда-нибудь подключат к
  `collision_monitor` вместо `_mult`, топики молча не законнектятся.

## Логика фильтрации

Класс `_RangeFilter` (идентичен в обоих узлах) — конвейер из четырёх стадий:

1. **Медиана по различающимся отсчётам**, окно `filter_window_size=3`
   (`statistics.median_low`), отсекает одиночные выбросы (перекрёстные
   наводки между соседними датчиками).
2. **Deadband** (`deadband_m=0.03`) — опубликованное значение двигается,
   только когда медиана уходит от него более чем на deadband; убирает
   дребезг в 10-15 см, оставшийся после медианы, без задержки сходимости,
   характерной для скользящего среднего.
3. **Гистерезис у `max_range`** (`range_hysteresis_m=0.05`) — триггер
   Шмитта вокруг границы диапазона, чтобы цель на краю дальности не
   заставляла статус «в диапазоне/нет» мигать каждый цикл.
4. **Hold-time** (`hold_time_s=0.6`) — пропажу эха на один-два цикла не
   считает потерей детекта; после `hold_time_s` без валидного эха история
   сбрасывается и публикуется `inf`.

На входе фильтра ошибка чтения (`-1`) и «эхо не вернулось» (`0xFFFF`) обе
дают `raw_m = inf`, но различаются **до** него: драйвер считает подряд идущие
неудачные опросы (`SonarReading.consecutive_errors`) и возраст последнего
опроса (`age_s`), и при превышении `bus_error_threshold` / `max_reading_age_s`
узел выдаёт `min_range` (fail-safe) и `ERROR` в `/diagnostics` вместо
показания фильтра.

## Известные проблемы и замечания

### Safety-relevant (влияют на обход препятствий рядом с людьми)

1. **Отказ шины неотличим от «пути свободен».** И `sonar_driver.cpp`, и оба
   Python-узла на верхнем уровне сводят «таймаут/ошибка чтения» (`-1`) и
   «эхо не вернулось, т.к. цели нет» (`0xFFFF`) к одному и тому же `range=inf`
   → `no_detection_value` (по умолчанию тоже `inf` на железе, см.
   `hardware.launch.py:174-186`, `publish_inf_as_out_of_range: True`). Это
   значение напрямую скармливается полигонам `nav2_collision_monitor`
   `SonarStopFront`/`SonarSlow`
   (`guide_robot_navigation/generated_config/first_iter_nav2.yaml:572-589`).
   Если отвалится кабель/разъём купола и **все** датчики начнут стабильно
   возвращать `-1`, слой sonar-защиты молча и полностью отключится — робот
   будет видеть «чистый путь» вплотную к препятствию/человеку, и никакого
   fault-топика/diagnostics об этом не будет. Единственный след — счётчики
   `_status` в `sonar_node_mult.py`, но их логирование по умолчанию выключено
   (см. выше).

   ✅ **Исправлено.** Драйвер считает `consecutive_errors` на опрос;
   `bus_error_threshold` (3) → публикуется `min_range` + `ERROR` в
   `/diagnostics`. Счёт в драйвере, а не по тикам публикации (иначе одна
   потерянная посылка = 5 «ошибок» и ложный стоп).

2. **Открытие порта без эксклюзивной блокировки.** `open_port()`
   (`sonar_driver.cpp:60-107`) не выставляет `TIOCEXCL`/`flock` на fd. Это не
   гипотетика: `guide_robot_bringup/launch/test.launch.py:14-17` подключает
   `hardware.launch.py`, который по умолчанию (`launch_sonar:=true`) уже
   поднимает `sonar_node_mult.py` на `/dev/tty_sonar`, а затем
   `test.launch.py:24-27` **отдельно** запускает ещё и `sonar_node.py` на том
   же порту — два независимых процесса одновременно пишут/читают один UART.
   При совпадении по времени команда одного узла и ответ на команду другого
   перемешиваются, что либо роняет checksum (читается как ошибка → см. п.1),
   либо в редком случае даёт совпавший по случайности checksum на чужих
   данных — то есть в SonarStopFront/SonarSlow может попасть мусорное
   расстояние. Дополнительно оба узла регистрируются под одинаковым именем
   `sonar_node`, что само по себе некорректно в ROS 2 graph.

   ✅ **Исправлено.** `ioctl(TIOCEXCL)` в `open_port()` (при неудаче — отказ
   старта), второй узел убран из `test.launch.py`.

3. **Числовое значение `range` может превышать заявленный `max_range` из
   того же сообщения.** Гистерезис (`_RangeFilter.update`,
   `sonar_node_mult.py:73-84` / `sonar_node.py:79-90`) держит состояние
   «в диапазоне» вплоть до `median_m > max_range + range_hysteresis_m` и в
   этом окне публикует реальную медиану как валидное числовое расстояние,
   хотя `msg.max_range` в этом же сообщении равен номинальным 2.0 м. Это
   нарушает конвенцию `sensor_msgs/Range` (валидное `range` должно лежать в
   `[min_range, max_range]`) и создаёт ловушку именно того рода, о которой
   предупреждает собственный комментарий к параметру
   `publish_inf_as_out_of_range` (`sonar_node_mult.py:112-116`): наивный
   потребитель с проверкой `range > max_range` молча отбросит эти показания,
   даже если сам узел считает их «в диапазоне».

   ✅ **Исправлено.** Публикуемое значение зажато `min(median_m, max_range)`;
   гистерезис по-прежнему решает «в диапазоне/нет», но наружу не выходит.

4. **Латентность обновления датчика хуже, чем задокументировано в
   штатном режиме.** Цикл опроса — `sonar_driver.cpp:182-203`: до 30 мс
   выдержки после каждого запроса плюс до 60 мс таймаута чтения
   (`read_bytes(..., 60)`, `sonar_driver.cpp:148`) на **каждый** из 7
   датчиков. В штатном режиме (эхо приходит быстро) это действительно даёт
   заявленные в докстринге ~200-250 мс на полный круг, но при деградации
   (часть датчиков систематически не отвечает/таймаутит) полный круг может
   доходить до ~630 мс. `source_timeout` у `collision_monitor` — всего 0.5 с
   (`first_iter_nav2.yaml:556`), т.е. именно в условиях плохого акустического
   отклика (что обычно совпадает с сильными помехами/сложной геометрией)
   sonar-источник рискует помечаться Nav2 как устаревший/недоступный —
   защита пропадает как раз тогда, когда она нужнее всего. Полигон
   `SonarStopFront` при этом всего 0.4 м в глубину
   (`first_iter_nav2.yaml:575`), так что запас по времени на такую
   деградацию крайне мал.

   ✅ **Исправлено, но диагноз в пункте был неточен.** `source_timeout` не
   срабатывал никогда: узел публикует 20 Гц со штампом `now` независимо от
   шины, то есть проблема была не в «устаревшем источнике», а в старом
   измерении под свежим штампом. Сделано: (A) общий дедлайн на ответ вместо
   таймаута на каждый `poll()` (было до 5×60 мс на датчик), сам таймаут
   остался 60 мс; (C) короткий backoff вместо выдержки только когда запрос
   не ушёл в порт (`-2`), после таймаута выдержка сохранена;
   (D) `SonarReading.age_s` + `max_reading_age_s` (0.75 с) → тот же
   `min_range` fail-safe. Худший круг ~640 мс вместо неограниченного.
   `source_timeout` в nav2 не трогали — он мимо цели.

   ⚠️ Таймаут ответа задаёт максимальную дальность, которую датчик успевает
   доложить: `(timeout_ms - 8.3) / 1000 * 343 / 2` — 60 мс ≈ 8.9 м, 30 мс
   ≈ 3.7 м. Считать его надо от диапазона датчика, а не от `max_range` узла.
   Снижение до 30 мс на железе загнало передние датчики, смотревшие в
   открытое пространство дальше 3 м, в постоянный отказ и остановило робота.

5. **`activate_dome()` не проверяет подтверждение и возврат `write()`**
   (`sonar_driver.cpp:118-129,144`) — при частичной записи/ошибке USB-serial
   адаптера в лог всё равно попадёт «🚀 Sonar dome is active», хотя купол мог
   не активироваться вовсе; узел при этом не имеет способа сообщить ROS-графу
   «датчики не инициализированы» (нет диагностик, ошибка порта идёт в
   `std::cerr`/`std::cout` из C++ pybind-модуля, а не через `rclcpp`/`rclpy`
   логгер — `sonar_driver.cpp:33,37`).

   ✅ **Исправлено.** Возврат `write()` проверяется, флаг `is_dome_active()`
   проброшен в Python → `ERROR` в лог и в `/diagnostics`. Подтверждения в
   протоколе нет, так что это «команда ушла в порт», не «купол проснулся».

### Прочее / сопровождение

6. **Несогласованная документация единиц измерения.** Заголовок драйвера
   утверждает `distance_mm` (`sonar_driver.hpp:22-24`), но по факту это счёт
   времени пролёта эха, требующий калибровочных `range_scale`/`range_offset`
   в Python — см. «Аппаратный интерфейс». Вводит в заблуждение при чтении
   только C++-части.

   ✅ **Исправлено.** Комментарий в `sonar_driver.hpp` описывает счётчик TOF.

7. **`min_range` не применяется как порог отсечения.** `raw_m = max(0.0,
   counts*range_scale+range_offset)` (`sonar_node_mult.py:214`,
   `sonar_node.py:212`) может быть меньше `min_range` (0.1 м) и всё равно
   публикуется как реальное расстояние. Направление ошибки безопасное
   (сообщает «слишком близко» вместо «нет данных»), но формально нарушает
   контракт `sensor_msgs/Range`.

   ✅ **Исправлено.** Валидное числовое показание зажато снизу `min_range`.

8. **Маппинг ID→frame продублирован** в двух файлах без общего источника
   правды (`sonar_node.py:136-144`, `sonar_node_mult.py:134-144`) — при
   изменении проводки/подключения нужно синхронно править оба, риск
   рассинхронизации и неверной маркировки, какой физический датчик что видит.

   ✅ **Исправлено.** `scripts/sonar_mapping.py` (`SONAR_MAPPING`), ставится
   через `install(FILES ...)` рядом с узлами.

9. **Пропущена зависимость `geometry_msgs` в `package.xml`.**
   `sonar_node.py:39` делает `from geometry_msgs.msg import Point`, но
   `package.xml` объявляет только `rclcpp`, `rclpy`, `sensor_msgs`,
   `visualization_msgs`, `guide_robot_msgs`. Сейчас работает только потому,
   что `visualization_msgs` тянет `geometry_msgs` транзитивно.

   ✅ **Исправлено.** Добавлены `geometry_msgs` и `diagnostic_msgs`.

10. **Захардкожен путь установки Python-модуля.**
    `CMakeLists.txt:29-31` ставит `furo_sonars_cpp` в
    `lib/python3.10/site-packages` вместо использования переменной
    ament/CMake для пути Python-пакетов. Работает только пока целевая
    система — Ubuntu 22.04/Python 3.10; при смене версии Python модуль
    перестанет импортироваться (`ImportError` при старте узла, а не
    «неверные показания» — упадёт сразу).

    ✅ **Исправлено.** `DESTINATION lib/${PROJECT_NAME}` — рядом со скриптами,
    которые импортируют модуль.

    ⚠️ `${PYTHON_INSTALL_DIR}` для этого не годится, проверено на железе: на
    Orin он резолвится в `local/lib/python3.10/dist-packages`, а env-hook
    воркспейса кладёт в `PYTHONPATH` путь `lib/python3.10/site-packages`.
    Модуль ставится мимо `PYTHONPATH`, а старая копия остаётся лежать
    (colcon не удаляет файлы, которые сборка перестала производить) и
    продолжает импортироваться — пересборка «не помогает», причина не видна.
    Каталог скриптов — это `sys.path[0]`, он приоритетнее `PYTHONPATH` и не
    зависит от того, как `sysconfig` резолвит `purelib`.

11. **`get_parameter(...)` вызывается на каждый тик `publish_ranges()`**
    (до 20 Гц) вместо кэширования/callback на изменение параметра — не
    баг, но лишние накладные расходы в самом горячем пути узла.

    ✅ **Исправлено.** Все параметры читаются один раз в `__init__`.

12. Логи C++-драйвера идут с эмодзи через `std::cout`/`std::cerr`
    (`sonar_driver.cpp:33,37,114,123,128`), а не через ROS-логгер — не
    фильтруются по уровню, не попадают в `ros2 launch` structured log,
    что дополнительно затрудняет диагностику отказа порта (см. п.5).

    ✅ **Исправлено.** `set_info_logger`/`set_error_logger`, узлы пробрасывают
    `rclpy`-логгер; `std::cerr` остался только как fallback вне ROS.

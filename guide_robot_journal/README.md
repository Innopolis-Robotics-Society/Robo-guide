# Журнал состояния робота

Отдельный процесс C++17 / ROS 2 Humble. Один `SingleThreadedExecutor` принимает
данные и обновляет заранее выделенные кэши; один поток формирует JSONL и работает
с диском. Очереди снимков и событий раздельные, ограниченные SPSC. При заполнении
отбрасывается новая запись, потери видны в диагностике. События обслуживаются
приоритетно, но очередь снимков не голодает.

**Рабочие топики ещё не выбраны:** `config/journal.yaml` содержит `sources: []`
и закомментированные примеры. Без источников пишется только собственное состояние
логгера. Логгер не запускается автоматически и не влияет на разрешение движения.

## Запуск и конфигурация

```bash
ros2 launch guide_robot_journal journal.launch.py journal_config:=/absolute/path/journal.yaml
# Вместе со штатным стеком (по умолчанию launch_journal=false):
ros2 launch guide_robot_bringup robot.launch.py launch_journal:=true journal_config:=/absolute/path/journal.yaml
```

Конфигурация читается при запуске, неизвестные ключи и несовместимые лимиты
отклоняются. Для изменения источников перезапускается только журнал.

Начальный профиль: снимок 5 с, свежесть 1 с, буфер 64 КиБ / сброс 1 с,
`fdatasync` 10 с, ротация 20 МиБ или 1 час, максимум 168 завершённых файлов,
возраст 7 суток, общий объём 1 ГиБ с учётом активного файла, резерв 128 МиБ.
Это стартовые настройки для испытаний, а не подтверждённый профиль робота.
События ускоряют сброс буфера в ОС; это **не** немедленный `fdatasync`.

| Адаптер | ROS-тип / сохранённые значения |
|---|---|
| `string` | `std_msgs/msg/String`: строка; события при изменении |
| `bool` | `std_msgs/msg/Bool`: значение; события при изменении |
| `battery` | `sensor_msgs/msg/BatteryState`: напряжение, ток, доля заряда, ёмкость, температура, присутствие, статус и health |
| `twist` | `geometry_msgs/msg/Twist`: все компоненты линейной и угловой скорости |
| `odometry` | `nav_msgs/msg/Odometry`: позиция, ориентация и скорости |
| `mission` | `guide_robot_msgs/msg/MissionState`: состояние, прерывание, пауза, тур, остановка и опубликованная причина; события переходов |
| `diagnostics` | `diagnostic_msgs/msg/DiagnosticArray`: отдельный кэш каждого `(source, name, hardware_id)` |
| `serialized` | Произвольный установленный ROS-тип: полное CDR-сообщение без разбора |
| `arrival` | Произвольный установленный ROS-тип: только факт поступления, счётчик и свежесть |

Общие поля источника: `id`, абсолютный `topic`, `adapter`, `stale_s`, `events`,
`reliability: best_effort/reliable`, `durability: volatile/transient_local`, `depth`.
Для `serialized`/`arrival` обязателен `type`, например `sensor_msgs/msg/LaserScan`.
Типизированный адаптер сам определяет тип. `stale_s: 0` отключает таймаут для
состояний, публикуемых лишь при изменении. Изменение уровня/сообщения диагностики
образует событие; дополнительные строковые ключи выбираются через `event_fields`.
Обычные изменения температуры или счётчиков без изменения этих признаков не
порождают события. `events: false` отключает события состояния, но не события
устаревания и нарушения лимитов входа.

Сохраняются последние доступные значения: общий `snapshot_id` не означает
синхронное измерение всех источников. `freshness` и состояние устройства независимы.
Частичная диагностика не удаляет отсутствующие в данном сообщении компоненты.
Компоненты не вытесняются автоматически: при заполнении пула новые ключи
пропускаются, увеличивая `input_limits`. Лимит обрабатываемых статусов ограничивает
работу одного callback.

## Лидары целиком

```yaml
sources:
  - id: lidar_left
    topic: /scan_left             # пример; рабочий список будет выбран отдельно
    adapter: serialized
    type: sensor_msgs/msg/LaserScan
    reliability: best_effort
    depth: 2
    max_bytes: 65536
    stale_s: 2.0
    stream: false
```

`stream: false` сохраняет последний **полный** скан в каждом снимке.
`stream: true` дополнительно сохраняет каждое доставленное сообщение; оно проходит
через очередь снимков, не вытесняя события. Массивы лучей и интенсивностей,
header и все остальные поля остаются в CDR без прореживания, округления и потери
NaN/Infinity. Работает также для других типов, например PointCloud2, если их
полный размер помещается в явно увеличенные лимиты.

При превышении `max_bytes` отбрасывается **всё сообщение**, а не часть лучей.
Старый скан не выдаётся за новый: payload становится недоступен, счётчик потерь
входных данных растёт, публикуется событие `payload_rejected`; повторяющиеся
нарушения не создают новых одинаковых событий. При возврате допустимого размера
создаётся `payload_restored`. Полная доставка каждого скана всё равно зависит от
QoS, DDS и доступности очереди; это не замена rosbag для гарантированного захвата.

В JSONL используются `encoding: cdr-base64`, `byte_length` и `data`.
Base64 увеличивает размер бинарного сообщения примерно на треть. В режиме каждого
скана объём истории может быть существенно меньше семи суток из-за общего лимита.

```bash
python3 tools/extract_cdr.py path/to/file.jsonl lidar_left 123 /tmp/scan.cdr
# В ROS Python, с установленным исходным типом:
# from rclpy.serialization import deserialize_message
# from sensor_msgs.msg import LaserScan
# scan = deserialize_message(Path('/tmp/scan.cdr').read_bytes(), LaserScan)
```

Утилита не перезаписывает существующий выходной файл. `sequence` выбирается внутри
нужного файла/экземпляра процесса.

## Формат, ресурсы и хранение

Каждая строка: `schema_version=1`, `instance_id`, `sequence`, тип
`event/snapshot/sample`, `snapshot_id`, источник, ROS-тип, время UTC/монотонное/ROS
в наносекундах, время последнего получения, счётчик, наблюдаемая частота и свежесть.
`source_stamp_ns=null`, если stamp не извлекался: generic-приём не разбирает CDR.
Для компактных записей доступны `component`, `hardware_id`, `level`, `text`, `fields`.
Числа остаются числами; нечисловые NaN/Infinity компактных полей представлены `null`.
Строки — UTF-8, повреждённые/обрезанные последовательности заменяются на U+FFFD.

События могут обогнать снимки при записи. Для восстановления порядка используйте
`instance_id` и `sequence`, не только физический порядок строк. Неизменные состояния
не создают новые события; их повторы видны в накопительном `unchanged_messages`.

Короткие строки и поля имеют фиксированные пределы: 16 полей, ключ до 31 байта,
значение до 95, текст до 255. Для диагностики ключ компонента до 95 байт и hardware
до 63; слишком длинные ключи компонентов отвергаются целиком, исключая слияние
разных компонентов после обрезки. Обрезание данных помечается `truncated`, лишние
статусы/поля и отклонённые сообщения отражаются в `input_limits`.

Настройка `memory_budget` проверяется до подписок. При старте выводится оценка
памяти собственных кэшей, очередей, буферов и ограниченного индекса файлов.
Слоты снимков рассчитаны на самый большой настроенный payload; увеличение
`max_bytes` увеличивает стоимость каждого слота. Увеличивайте бюджет или уменьшайте
число слотов явно. Чтобы избежать штатных потерь, ёмкость очереди должна учитывать
число записей в одном снимке и всплески потока сканов.

**Это не лимит RSS всего процесса:** память ROS/DDS, входящих сообщений,
аллокаторов и библиотек учитывается отдельно. Generic-подписка всё равно получает
каждое сообщение; уменьшение частоты снимков не уменьшает частоту DDS-доставки.

Каталог принадлежит одному писателю (`flock`). Логгер открывает файлы с правами
0600, активный файл имеет суффикс `.open`. При рестарте удаляется неполный хвост до
последнего перевода строки, файл завершается, затем применяются лимиты хранения.
Незавершённая операция завершения файла также восстанавливается. Возраст берётся
по времени последней записи, а не по имени; восстановление не омолаживает файл.

Удаляются только обычные файлы `robotlog-<UTC ns>-<pid>-<counter>.jsonl`.
Символические ссылки и посторонние файлы пропускаются. Индекс ограничен числом
удерживаемых файлов; огромная старая история не загружается целиком в память.
Общий объём учитывает активный файл. Перед записью проверяется резерв места;
другие процессы также могут расходовать накопитель, поэтому ошибки записи
обрабатываются отдельно. Недоступный диск не блокирует подписки: записи теряются
с явным счётчиком, повтор открытия делается с настраиваемой задержкой.
Неопределённо записанные порции автоматически не повторяются.

Самодиагностика `/robot_journal/diagnostics` и собственная запись `__journal`
появляются каждые 5 секунд: размер/максимум очередей, потери, ограничения входа,
ошибки и errno диска, объём, удалённые файлы, число записей и максимальная
наблюдавшаяся длительность callback (`max_callback_ns`). Собственная диагностика
исключена из источников. `written_records` означает передачу ОС, не гарантию
сохранности при внезапном отключении питания.

## Проверки и настройка на роботе

```bash
colcon build --packages-up-to guide_robot_journal
colcon test --packages-select guide_robot_journal --event-handlers console_direct+
colcon test-result --verbose
```

Тесты покрывают SPSC-переполнение и порядок, JSON/Unicode/CDR, лимиты памяти,
ротацию, возраст, общий объём, резерв диска, захват каталога, ссылки,
аварийный хвост, завершение записи, полные лидары и частичную диагностику при
остановленном ROS time. CI запускает suite отдельным шагом.

После выбора топиков сравнить одинаковый сценарий без логгера и с ним: CPU/RSS,
I/O (`pidstat -u -r -d`), диагностические счётчики и задержки управляющего стека.
Отдельно провести длительный прогон, всплеск событий, медленный диск и внезапное
завершение процесса. Процент CPU и рабочий срок хранения до этих измерений не
обещаются. Примерный расход полного потока: `размер CDR × частота × 4/3` плюс
метаданные JSON, события и снимки.

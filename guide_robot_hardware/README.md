# guide_robot_hardware

Пакет на **C++17** (не Python — корневой `README.md` репозитория в этом
устарел, см. раздел «Известные проблемы»). Это `hardware_interface`-плагин
`ros2_control`, а не отдельный ROS-узел: класс `GuideRobotSystem`
(`include/guide_robot_hardware/guide_robot_system.hpp`,
`src/guide_robot_system.cpp`) реализует
`hardware_interface::SystemInterface` и загружается процессом
`controller_manager` (`ros2_control_node`) через `pluginlib` по имени
`guide_robot_hardware/GuideRobotSystem`
(`guide_robot_hardware.xml:4-6`). Пакет напрямую говорит с реальными
приводными моторами базы Guide-Robot по UART/RS-485 — это единственное место в
репозитории, где команды скорости превращаются в байты на шине.

## Обзор

- Один `SystemInterface` на два колёсных сустава: `left_wheel_joint`,
  `right_wheel_joint` (`export_state_interfaces`/`export_command_interfaces`,
  `guide_robot_system.cpp:226-248`).
- Состояния: `position`, `velocity` (рад, рад/с) на каждое колесо; команды —
  только `velocity`.
- Подключается через `guide_robot.ros2_control.xacro`
  (`guide_robot_description/urdf/guide_robot.ros2_control.xacro:61-77`) как
  один из трёх бэкендов (`use_sim` → Gazebo, `use_mock_hardware` → заглушка,
  иначе — этот плагин). Параметры берутся из
  `guide_robot_description/config/robot_params.yaml`, секция `drive`
  (порт, ID моторов, коэффициенты, `cmd_timeout`).
- `controller_manager` поднимает компонент в состоянии `unconfigured`
  (`guide_robot_description/config/controllers.yaml.in:10-12`) — активацию
  должен явно выполнить внешний код (супервизор/скрипт), сам плагин себя не
  переводит в `active`.
- Верхнеуровневый лимит скорости задаёт не этот пакет, а
  `diff_drive_controller` (лимиты `linear.x.*`/`angular.z.*` в
  `controllers.yaml.in:45-52`, из `robot_params.yaml: limits`). Плагин из
  этого README получает уже отфильтрованные команды на колёса.

## Интерфейс ros2_control

Жизненный цикл реализован полностью (`guide_robot_system.hpp:27-43`):

- **`on_init`** — парсит `info_.hardware_parameters` (`serial_port`,
  `baud_rate`, `left_wheel_id`, `right_wheel_id`, `left_sign`, `right_sign`,
  `speed_coefficient` обязательны через `.at()`; `swap_drives`,
  `wheel_radius`, `ticks_per_rev`, `cmd_timeout` опциональны) —
  `guide_robot_system.cpp:79-97`.
- **`on_configure`** — открывает serial-порт (`O_RDWR|O_NOCTTY|O_SYNC`),
  настраивает termios (8N1, raw, `VMIN=0/VTIME=0` — неблокирующее чтение без
  `O_NONBLOCK` на весь fd) — `guide_robot_system.cpp:113-158`.
- **`on_activate`** — сбрасывает буферы/счётчики, запускает поток
  сторожевого таймера (`startWatchdog()`) — `guide_robot_system.cpp:160-183`.
- **`on_deactivate`** — останавливает сторож, **явно отправляет** пакет
  нулевой скорости (комментарий в коде верно объясняет зачем: драйвер FURO
  держит последнюю принятую скорость до следующего пакета, обнулить поля в
  памяти недостаточно) — `guide_robot_system.cpp:185-206`.
- **`on_cleanup`** — закрывает порт (`closePort()`), симметрично
  `on_configure`, а не `on_deactivate` — сделано осознанно, чтобы цикл
  `deactivate → activate` (штатная операция `controller_manager`) не терял
  открытый fd (см. комментарий `guide_robot_system.hpp:39-41`).
- **`read()`/`write()`** вызываются из RT-потока `controller_manager` на
  `update_rate: 50` (`robot_params.yaml:70`, т.е. период 20 мс).

## Взаимодействие с реальным приводом

Протокол — вариация Dynamixel 1.0 (`0xFF 0xFF <ID> <LEN> <INSTR> ... <CHK>`,
`checksum = ~sum(body) & 0xFF`, `guide_robot_system.cpp:50-56`), но с
проприетарной инструкцией FURO `0x06` вместо стандартного Sync Write
(комментарий `guide_robot_system.cpp:405`), так что это не настоящая
Dynamixel-прошивка, а её протокольный клон.

- **`write()`** (`guide_robot_system.cpp:450-469`) на каждом цикле собирает
  18-байтный broadcast-пакет (ID `0xFE`) со скоростями обоих моторов и
  фиксированным ускорением `ACCEL = 1000` (`guide_robot_system.cpp:399`,
  хардкод, не связан с `max_linear_accel`/`max_angular_accel` из
  `robot_params.yaml` — это отдельный, не документированный здесь параметр
  прошивки драйвера). Слоты пакета адресуются позицией, а не ID
  (проверено на железе — коммент `guide_robot_system.cpp:457-461`), поэтому
  `swap_drives` переставляет местами именно источник команды.
- **`read()`** (`guide_robot_system.cpp:276-381`) раз в 5 циклов (~10 Гц)
  шлёт запрос регистра энкодеров мотору `left_wheel_id_`, ответ (19 байт)
  по протоколу содержит тики обоих моторов сразу (слот 1/слот 2 —
  позиционно, как в `write()`). Скорость считается делением дельты позиции
  на время с последнего **успешно разобранного** пакета (`enc_elapsed_`), а
  не на период цикла — иначе скорость была бы завышена впятеро (это уже
  когда-то было живым багом, см. комментарий `guide_robot_system.cpp:122-125,
  333-335`).
- Единиц скорости: `рад/с → м/с` через `wheel_radius_`, затем `→ units`
  через `speed_coefficient_` (эмпирически откалиброван на роботе,
  `robot_params.yaml:136-142`), результат клампится в диапазон `int16_t`
  (`toMotorUnits`, `guide_robot_system.cpp:383-392`).

## Известные проблемы и замечания

### Безопасность — сторожевой таймер (watchdog) выключается молча

`cmd_timeout` по умолчанию `0.0` (`guide_robot_system.hpp:100`), и при
`cmd_timeout <= 0.0` `startWatchdog()` **не запускает поток**, а просто
пишет `RCLCPP_WARN` и продолжает как ни в чём не бывало —
`guide_robot_system.cpp:477-483`. `on_activate` при этом всё равно
возвращает `SUCCESS` (`guide_robot_system.cpp:160-183`): компонент активно
работает и крутит моторы, при этом при зависании управляющего цикла
(`controller_manager`, планировщик, DDS и т.п.) **последняя переданная
скорость будет держаться приводом бесконечно** — драйвер FURO, как отмечено
в самом коде (`guide_robot_system.cpp:192-193`), не имеет собственного
таймаута команд. В штатной конфигурации `robot_params.yaml: drive.cmd_timeout:
0.3` (`robot_params.yaml:62`) это исправлено, но защита целиком зависит от
того, что параметр не забудут передать/не собьют при рефакторинге xacro —
никакой проверки на уровне плагина нет (`on_activate` не отказывает при
`cmd_timeout<=0`, хотя мог бы). Учитывая, что это управляет 62-килограммовой
базой рядом с людьми, отсутствие watchdog должно как минимум быть
жёстким `ERROR` при активации, а не тихим `WARN`.

### Безопасность — клэмп скорости в плагине по факту отсутствует

`toMotorUnits` ограничивает результат только диапазоном `int16_t`
(`guide_robot_system.cpp:388-390`), что соответствует ~5.6 м/с линейной
скорости колеса при текущем `speed_coefficient` — почти в 10 раз выше
`limits.max_linear_velocity: 0.6` из `robot_params.yaml:42`. Реальная защита
от завышенной скорости целиком лежит на `diff_drive_controller`
(`SpeedLimiter`, лимиты из `controllers.yaml.in:45-52`) и на объявленных
`min`/`max` в `command_interface` xacro
(`guide_robot.ros2_control.xacro:38-41`) — но эти `min`/`max` в самом
`hardware_interface` ни на что не влияют, это просто метаданные для тех, кто
их прочитает. Если когда-либо к этим же command interface подключится
другой контроллер (например, `forward_command_controller` для отладки) без
собственного лимитера, у `GuideRobotSystem` нет ни одного рубежа защиты
между «странной командой» и «пятикратно превышенной скоростью на колесе».
Стоит добавить независимый клэмп по `max_linear_velocity`/эквиваленту в
самом плагине как defense-in-depth.

### Блокирующий вызов в RT-цикле `read()`

`usleep(5000)` в `read()` (`guide_robot_system.cpp:290`) выполняется каждый
5-й цикл (примерно 10 Гц) и на 5 мс блокирует поток `controller_manager` —
это четверть бюджета цикла при `update_rate=50` (период 20 мс). Комментарий
объясняет обоснование (нужно дождаться ответа энкодеров на шине,
~2.4 мс на 115200 бод), но `usleep`/сон вместо `poll()`/`select()` с
таймаутом в реальном RT-контуре — плохая практика: это детерминированная,
но нефункциональная потеря времени цикла, которая может конкурировать с
другими hardware-компонентами/контроллерами на том же `controller_manager`
и увеличивать джиттер именно тогда, когда координация с другими системами
(навигация, safety) наиболее важна.

### Гонка между watchdog-потоком и `read()`

Комментарий у `serial_mutex_` утверждает, что мьютекс — «единственный на
все `::write` в порт» и что `watchdogLoop()` пишет параллельно с
`read()`/`write()` (`guide_robot_system.hpp:88-90`). Это верно для
`sendEncoderRequest()` и `writeSpeedPacket()` (обе берут `serial_mutex_`),
но сырой `::read(serial_fd_, buf, sizeof(buf))` в `read()`
(`guide_robot_system.cpp:295`) **не берёт мьютекс вообще**. Если сторож
одновременно шлёт нулевой пакет (после срабатывания таймаута) — это не
падение и не порча памяти (fd на чтение/запись из разных потоков — штатная
POSIX-операция), но по факту нарушает заявленную в комментарии
инвариантность "мьютекс защищает весь обмен по порту" и на
RS-485-полудуплексе теоретически может исказить окно приёма ответа
энкодеров commандным пакетом, ушедшим "поперёк" — на практике должно просто
проявляться как отброшенный по checksum кадр, не более, но стоит привести
код и комментарий в соответствие.

### Отсутствие диагностики отказа энкодеров

`read()` всегда возвращает `hardware_interface::return_type::OK`
(`guide_robot_system.cpp:380`), даже если ни один валидный пакет энкодеров
ни разу не был разобран (`initialized_encoders_` остаётся `false` сколь
угодно долго). При этом `write()` никак не зависит от состояния энкодеров и
продолжает слать команды скорости открытым циклом
(`guide_robot_system.cpp:450-469`) — то есть при физически отключённом или
неисправном энкодер-каскаде **робот будет ехать**, а `left_position_`/
`right_velocity_` в `/joint_states` останутся замороженными на нуле,
молча вводя в заблуждение одометрию, EKF и Nav2. Нет ни счётчика подряд
идущих неудачных попыток чтения, ни эскалации в диагностику/лог уровня
ERROR, ни возврата `ERROR` из `read()`, который `controller_manager` мог бы
использовать для перевода компонента в `unconfigured`.

### Прочее (не safety-critical)

- `on_configure` не проверяет коды возврата `tcgetattr`/`tcsetattr`
  (`guide_robot_system.cpp:135, 153`) — тихий отказ настройки порта.
- `on_init` использует `std::stoi`/`std::stod`/`.at()` на параметрах без
  `try/catch` (`guide_robot_system.cpp:79-97`); при отсутствующем или
  нечисловом параметре в xacro исключение всплывает из `on_init` без
  диагностики о том, какой именно параметр виноват.
- `package.xml` содержит placeholder-описание `TODO: Package description`
  (`package.xml:6`) — стоит заполнить, раз пакет управляет реальными
  моторами.
- `CMakeLists.txt` содержит комментарии-чеклисты вида `# ← добавь`
  (`CMakeLists.txt:11,12,17,24,32,36`) — судя по всему, остаток от
  пошаговой инструкции/туториала по написанию `hardware_interface`-плагина,
  стоит убрать перед тем, как показывать код внешним ревьюерам.
- Хардкод `ACCEL = 1000` (`guide_robot_system.cpp:399`) — единицы и смысл
  этого параметра прошивки нигде не задокументированы; стоит либо вынести
  в параметр компонента, либо явно описать, во что переводится это число.

## Что сделано хорошо

Стоит явно отметить и позитивные решения: явная отправка стоп-пакета в
`on_deactivate` и в деструкторе (последний рубеж на случай `SIGINT`,
`guide_robot_system.cpp:60-69`), симметричный `on_cleanup`/`on_configure`
для избежания лишних переоткрытий порта, throttled-логирование
(`RCLCPP_*_THROTTLE`) вместо спама на каждый цикл, и в целом рабочий (при
корректно заданном `cmd_timeout`) сторожевой таймер с гистерезисным
логированием срабатывания/восстановления (`guide_robot_system.cpp:500-527`).

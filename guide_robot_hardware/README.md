# guide_robot_hardware

Пакет на **C++17**. Это `hardware_interface`-плагин
`ros2_control`, а не отдельный ROS-узел: класс `GuideRobotSystem`
(`include/guide_robot_hardware/guide_robot_system.hpp`,
`src/guide_robot_system.cpp`) реализует
`hardware_interface::SystemInterface` и загружается процессом
`controller_manager` (`ros2_control_node`) через `pluginlib` по имени
`guide_robot_hardware/GuideRobotSystem`
(`guide_robot_hardware.xml:4-6`). Пакет напрямую говорит с реальными
приводными моторами базы Guide-Robot по UART/RS-485 — это единственное место в
репозитории, где команды скорости превращаются в байты на шине.

## Обзор

- Один `SystemInterface` на два колёсных сустава: `left_wheel_joint`,
  `right_wheel_joint` (`export_state_interfaces`/`export_command_interfaces`,
  `guide_robot_system.cpp:424-446`).
- Состояния: `position`, `velocity` (рад, рад/с) на каждое колесо; команды —
  только `velocity`.
- Подключается через `guide_robot.ros2_control.xacro`
  (`guide_robot_description/urdf/guide_robot.ros2_control.xacro:68-90`) как
  один из трёх бэкендов (`use_sim` → Gazebo, `use_mock_hardware` → заглушка,
  иначе — этот плагин). Параметры берутся из
  `guide_robot_description/config/robot_params.yaml`, секция `drive`
  (порт, ID моторов, коэффициенты, `cmd_timeout`).
- `controller_manager` поднимает компонент **сразу в `active`**
  (`hardware_components_initial_state`,
  `guide_robot_description/config/controllers.yaml.in:10-16`), то есть
  `on_configure` + `on_activate` выполняются при старте launch, без чьей-либо
  команды. Это помечено в том файле как временный обход: компонент
  планировался в `unconfigured` под управлением супервизора, но интеграция
  супервизора с `ros2_control` не сделана — он умеет говорить только с
  `nav2_lifecycle_manager`. Практическое следствие: моторы поднимаются в обход
  супервизора, и единственное, что мешает им поехать при отсутствующем
  железе, — отказ `on_configure` (нет `/dev/tty_motors`) или `on_activate`
  (см. «Защиты уровня плагина»).
- Верхнеуровневый лимит скорости задаёт не этот пакет, а
  `diff_drive_controller` (лимиты `linear.x.*`/`angular.z.*` в
  `controllers.yaml.in:45-52`, из `robot_params.yaml: limits`). Плагин из
  этого README получает уже отфильтрованные команды на колёса, но с 2026-07-31
  имеет и собственный клэмп — см. «Защиты уровня плагина».

## Параметры компонента

Все приходят из `<hardware>` в
`guide_robot_description/urdf/guide_robot.ros2_control.xacro:68-90`, значения —
из `guide_robot_description/config/robot_params.yaml`.

**Обязательные** (отсутствие или нечисловое значение — отказ `on_init` с
указанием имени параметра, а не голое исключение из `std::stod`):
`serial_port`, `baud_rate`, `left_wheel_id`, `right_wheel_id`, `left_sign`,
`right_sign`, `speed_coefficient`, `cmd_timeout`, `max_wheel_velocity`.

Последние два обязательны намеренно: это единственные две защиты уровня
плагина, и «забыли передать при рефакторинге xacro» не должно молча означать
«защиты нет».

**Необязательные** (дефолты в `guide_robot_system.hpp` соответствуют текущему
железу): `swap_drives` (булев: принимает `1/0` и `true/false`, регистр не
важен; всё остальное — ошибка `on_init`), `wheel_radius`, `ticks_per_rev`,
`encoder_timeout` (с; `0` выключает детектор отказа энкодеров — при этом в лог
уходит `WARN`), `encoder_wrap_ticks` (`0` выключает ремонт разрывов счётчика —
тоже с `WARN`), `encoder_poll_divider`, `motor_accel`.

`encoder_poll_divider` считает **циклы управления**, а не секунды, и потому
неявно привязан к `update_rate`. При текущих 50 Гц делитель 5 даёт запрос раз в
100 мс — вдвое чаще, чем прошивка отдаёт кадры (~215 мс). Если менять
`update_rate`, делитель надо пересчитывать: при 10 Гц те же 5 дадут опрос раз в
500 мс, то есть реже периода прошивки, и половина кадров потеряется.

## Интерфейс ros2_control

Жизненный цикл реализован полностью (`guide_robot_system.hpp:26-48`):

- **`on_init`** — `loadParameters()` разбирает `info_.hardware_parameters`
  (см. «Параметры компонента»), проверяет диапазоны и возвращает `ERROR` при
  любой проблеме, перечислив в логе все неисправные параметры сразу.
- **`on_configure`** — открывает serial-порт (`O_RDWR|O_NOCTTY|O_SYNC`),
  настраивает termios (8N1, raw, `VMIN=0/VTIME=0` — неблокирующее чтение без
  `O_NONBLOCK` на весь fd). Коды возврата `tcgetattr`/`tcsetattr` проверяются,
  при отказе порт закрывается и возвращается `ERROR`. Идемпотентен: перед
  `open()` вызывается `closePort()`, иначе повторная конфигурация уже
  сконфигурированного компонента утекала бы дескриптором.
- **`on_activate`** — сбрасывает буферы/счётчики и запускает поток сторожевого
  таймера. **Отказывает (`ERROR`), если сторож запустить невозможно**
  (`cmd_timeout <= 0`): активный компонент без watchdog запрещён.
- **`on_deactivate`** — останавливает сторож, **явно отправляет** пакет
  нулевой скорости (комментарий в коде верно объясняет зачем: драйвер FURO
  держит последнюю принятую скорость до следующего пакета, обнулить поля в
  памяти недостаточно) — `guide_robot_system.cpp:383-403`.
- **`on_cleanup`** — закрывает порт (`closePort()`), симметрично
  `on_configure`, а не `on_deactivate` — сделано осознанно, чтобы цикл
  `deactivate → activate` (штатная операция `controller_manager`) не терял
  открытый fd (см. комментарий у `on_cleanup` в hpp).
- **`on_error`** — путь после `ERROR` из `read()`/`write()`. `ResourceManager`
  ведёт компонент в `unconfigured` **минуя `on_deactivate` и `on_cleanup`**,
  поэтому освобождение делается здесь и в том же порядке: снять сторожа →
  отправить стоп-пакет → закрыть порт. Без этого сторожевой поток продолжал бы
  писать в порт после отказа, а следующий `on_configure` открыл бы второй fd на
  тот же `/dev/tty_motors`.
- **`read()`/`write()`** вызываются из RT-потока `controller_manager` на
  `update_rate: 50` (`robot_params.yaml:91`, т.е. период 20 мс). Оба возвращают
  `ERROR`, если порт у активного компонента закрыт: это нарушение инварианта
  (активация без открытого fd отклоняется), и тихий `OK` означал бы замороженную
  одометрию, которую верхний стек примет за «робот стоит».

## Взаимодействие с реальным приводом

Протокол — вариация Dynamixel 1.0 (`0xFF 0xFF <ID> <LEN> <INSTR> ... <CHK>`,
`checksum = ~sum(body) & 0xFF`, `guide_robot_system.cpp:151-157`), но с
проприетарной инструкцией FURO `0x06` вместо стандартного Sync Write
(комментарий `guide_robot_system.cpp:837`), так что это не настоящая
Dynamixel-прошивка, а её протокольный клон.

- **`write()`** на каждом цикле собирает 18-байтный broadcast-пакет
  (ID `0xFE`) со скоростями обоих моторов и ускорением `motor_accel_`
  (параметр, дефолт `1000`; единицы прошивки FURO, вендором не
  задокументированы и с `max_linear_accel`/`max_angular_accel` из
  `robot_params.yaml` не связаны). Слоты пакета адресуются позицией, а не ID
  (проверено на железе — коммент в `write()`), поэтому `swap_drives`
  переставляет местами именно источник команды.
- **`read()`** раз в `encoder_poll_divider` циклов шлёт запрос регистра
  энкодеров мотору `left_wheel_id_`, ответ (19 байт) содержит тики обоих моторов
  сразу (слот 1/слот 2 — позиционно, как в `write()`). Скорость считается
  делением дельты позиции на время с последнего **успешно разобранного**
  пакета (`enc_elapsed_`), а не на период цикла — иначе скорость была бы
  завышена впятеро (это уже когда-то было живым багом, см. комментарий у
  `enc_elapsed_` в hpp).
- Транзакция «запрос → ожидание → чтение» целиком идёт под `serial_mutex_`,
  ожидание — через `poll()` с бюджетом `ENC_RESPONSE_BUDGET_MS = 5`. `poll()`
  возвращается сразу по приходу кадра; фиксированного сна в RT-цикле нет.
- Единиц скорости: `рад/с → м/с` через `wheel_radius_`, затем `→ units`
  через `speed_coefficient_` (эмпирически откалиброван на роботе,
  `robot_params.yaml:157-162`), результат клампится в диапазон `int16_t`
  (`toMotorUnits`, `guide_robot_system.cpp:799-826`).

## Защиты уровня плагина

Рубежи, добавленные 2026-07-31 по итогам разбора этого README (первые три) и
2026-08-06 (детектор отказа записи). Каждый рассчитан на то, что вышестоящий
слой (`diff_drive_controller`, `controller_manager`, супервизор) уже отказал.

### Сторожевой таймер команд

`cmd_timeout` — **обязательный** параметр, значение `<= 0` отклоняется дважды:
в `loadParameters()` и в `startWatchdog()`, и `on_activate` в этом случае
возвращает `ERROR`. Раньше здесь были `RCLCPP_WARN` и `SUCCESS`: компонент
активировался и крутил моторы вообще без сторожа, а у драйвера FURO своего
таймаута команд нет — зависший управляющий цикл означал 62 кг, едущие с
последней принятой скоростью до упора.

`watchdogLoop()` тикает раз в `min(20 мс, cmd_timeout/4)` — при штатных 0.3 с
это те же 20 мс, но при уменьшении таймаута период опроса теперь уменьшается
вместе с ним, а не остаётся сравнимым с самим таймаутом. При превышении
`cmd_timeout` шлёт нулевые скорости повторно (одиночный пакет мог не дойти) и
логирует срабатывание и восстановление с гистерезисом.

### Клэмп скорости на колесе

`toMotorUnits()` клампит команду по `max_wheel_velocity_` (обязательный
параметр) до пересчёта в units, и отдельно возвращает `0` на нефинитной
команде — `static_cast<int16_t>` от NaN это UB, а на шине — произвольная
скорость.

Значение приходит из xacro тем же выражением `w_wheel_max`, что и `min`/`max`
у `command_interface` — на текущем `robot_params.yaml` это **11.60 рад/с**
(≈1.19 м/с на колесе). Это конверт худшего случая `v_max + w_max·B/2` с
запасом 1.10, а не сам лимит: клэмп не должен резать легальные команды,
только ловить контроллер без лимитера.

Важно, почему этого мало без клэмпа: `min`/`max` в `command_interface`
(`guide_robot.ros2_control.xacro`) — **метаданные**, `hardware_interface` их не
применяет. Единственным ограничением в плагине был диапазон `int16_t`, а это
≈5.6 м/с на колесе при текущем `speed_coefficient` — то есть не защита вовсе.
Теперь если к тем же command interface подключится контроллер без
`SpeedLimiter` (например `forward_command_controller` для отладки), рубеж
есть.

### Детектор отказа энкодер-каскада

`read()` копит `enc_silence_` и обнуляет его **только** валидным разобранным
кадром. При `enc_silence_ > encoder_timeout` (по умолчанию 1.0 с, т.е. ~10
пропущенных кадров подряд, а не единичный сбой checksum) `read()` логирует
`ERROR`, **сам отправляет стоп-пакет** и возвращает
`hardware_interface::return_type::ERROR`.

Стоп-пакет отправляется явно, а не через `on_deactivate`: `ERROR` из `read()`
ведёт компонент через `on_error`, и проход по `on_deactivate` не гарантирован,
а драйвер FURO держит последнюю принятую скорость до следующего пакета.

Раньше `read()` всегда возвращал `OK`, а `write()` от состояния энкодеров не
зависел: при физически отключённом энкодер-каскаде робот ехал, а
`/joint_states` стояли на нуле. Для одометрии, EKF и Nav2 это не «нет данных»,
а «робот стоит» — ошибка молча уезжала вверх по стеку.

### Детектор отказа записи в порт

`write()` считает подряд идущие неудачи `writeSpeedPacket()`. Одиночная — это
`EAGAIN` на шине, она переживается молча (throttled-`WARN` уже есть внутри);
`WRITE_FAILURE_LIMIT = 10` подряд (200 мс при `update_rate: 50`) означают, что
команды до драйвера не доходят, и `write()` возвращает `ERROR`. Раньше
результат записи игнорировался целиком: порт мог быть мёртв, а Nav2 продолжал
считать, что робот исполняет команды.

Отметка времени для сторожа (`last_write_ns_`) обновляется **и при неудачной
записи** — это осознанно. Сторож ловит зависший управляющий цикл, а здесь цикл
жив и сломан порт; иначе сторож начал бы молотить стоп-пакетами в тот же
неисправный порт поверх этой диагностики.

### Ремонт разрывов счётчика драйвера

**Наблюдение (2026-08-05).** Во время SLAM одометрия единично «выстреливала» —
робот на карте разворачивался примерно на 52° и обратно не восстанавливался:

```
dt=220мс  dL=+0.2437  dR=-2.9198 рад  → курс -52.2°
```

Левое колесо в норме, правое «проехало» −2.9198 рад; вычитание π даёт +0.2218 —
ровно как у левого, то есть робот ехал прямо. А π рад на колесе при
`ticks_per_rev: 131072` — это ровно 65 536 тиков, 2¹⁶.

**Диагноз.** Не ошибка передачи: контрольная сумма кадра верна, и позиция здесь
абсолютная — битый кадр самокорректировался бы следующим же, а смещение
осталось навсегда. Значит уехал сам аккумулятор в прошивке FURO: 32-битная
позиция собирается из 16-битного аппаратного счётчика и программного старшего
слова, и заём при переходе через ноль иногда теряется. Правое колесо при
`right_sign: -1` проходит через ноль каждые ~0.32 м пути.

**Что делает `correctTickDelta()`.** Дельта в пределах полупериода счётчика
(2¹⁵ тиков) принимается как есть. Вышедшая за него сверяется с тремя
кандидатами — сама дельта и она же ±`encoder_wrap_ticks` — по физическому
конверту `max_wheel_velocity · dt`. Ни одного правдоподобного — кадр
отвергается целиком (позиции, `enc_elapsed_` и `enc_silence_` не трогаются:
для верхнего стека это «кадра не было», и подряд идущие отказы штатно доводят
до детектора тишины). Позиция считается из развёрнутого счёта — сырое значение
драйвера после разрыва остаётся смещённым.

Сверка идёт именно по физическому конверту, а не по полупериоду, и это не
мелочь: кадры приходят раз в ~215 мс (см. ниже), за это время колесо на
`max_linear_velocity` 0.9 м/с набирает 39 334 тика — больше полупериода 32 768.
Проверка по полупериоду отвергала бы каждый кадр прямой на полном ходу и валила
бы энкодер-каскад в ложный отказ.

Когда достижимых кандидатов несколько, выбирается ближайший к скорости на
прошлом принятом кадре: разрыв означал бы скачок скорости колеса на ~15 рад/с
за кадр, чего 62-килограммовая база не разгонит и не затормозит.

**Слепая зона.** Если разрыв утащил показание внутрь полупериода, оно по одному
кадру неотличимо от честного хода в другую сторону — информационный предел, а
не недоделка. Требует |v| > 7.31 рад/с (0.75 м/с на колесе) при каденции
215 мс; ниже этой скорости любой разрыв опознаётся однозначно.

Счётчики `enc_wrap_repairs_` / `enc_frames_rejected_` печатаются в сообщении
детектора тишины. Растущее число разрывов — деградация прошивки/железа, а не
норма: если оно набегает, вопрос к вендору, а не к этому коду.

### Каденция энкодеров: 4.6 Гц — это потолок прошивки

Замер на роботе 2026-08-05: медиана интервала между кадрами **215 мс**, min
196 мс. Потолок держим не мы:

- **Цикл здоров** — `/joint_states` и `/odom` идут ровно 50 Гц при
  `update_rate: 50`. 215 мс — темп ответов на шине, а не период цикла.
- **От частоты запросов не зависит** — при `encoder_poll_divider` 5 → 1 запросы
  участились впятеро, а темп кадров не сдвинулся (4.6 → 4.7 Гц). Коллизии или
  разрушенные ответы обязаны были бы зависеть от того, как часто мы передаём.
- **Мы ничего не теряем** — за окно в 100 запросов принято ровно 19 × число
  кадров байт, без единого лишнего: ни эха адаптера, ни обрубков, ни битых
  контрольных сумм.

Вывод: прошивка отдаёт позицию со своим внутренним периодом и на остальные
запросы молчит; опросом это не обходится. Поэтому `encoder_poll_divider: 5` —
`1` стоил бы 3.9 мс проводного времени на цикл вместо 0.8 за нулевую прибавку.

Следствие для навигации: TF `odom → base_footprint` отстаёт до ~215 мс,
наибольший наблюдённый шаг курса на кадр — 6.6°. Скан-матчер SLAM Toolbox это
переваривает (`coarse_search_angle_offset` ±20°). Если понадобится точнее —
либо другая прошивка/регистр, либо экстраполяция позиции между кадрами
(сознательно не сделана: это выдуманные данные в безопасностном тракте).

## Эксплуатационные замечания

- **Восстановление после отказа ручное.** Компонент уходит в ошибку и сам
  обратно в `active` не возвращается — переактивацию должен выполнить внешний
  код (супервизор). Отдельного авто-ретрая в плагине нет намеренно: повторный
  автоматический запуск моторов после необъяснённой потери обратной связи — не
  то поведение, которое стоит зашивать в железный слой. Внешнему коду нужен
  полный путь `configure → activate`: `on_error` оставляет компонент в
  `unconfigured` с закрытым портом, одной активации недостаточно.
- **`read()` держит `serial_mutex_` до 5 мс** на каждом пятом цикле. Стоп-пакет
  сторожевого таймера в это окно может задержаться на те же ≤5 мс — при
  `cmd_timeout = 0.3` это шум, но при уменьшении таймаута это надо помнить.
  Мьютекс теперь честно покрывает **весь** обмен по порту, включая `::read`;
  раньше комментарий это утверждал, а `::read` мьютекс не брал — на
  полудуплексном RS-485 стоп-пакет мог уйти поперёк окна приёма ответа.
- **Третий энкодер (байты 14..17 ответа) не декодируется.** В базе он не
  используется; раскладка кадра описана комментарием в `applyEncoderFrame()`.
- **Защиты этого README не распространяются на `use_sim`/`use_mock_hardware`** —
  там подключаются `gazebo_ros2_control/GazeboSystem` и
  `mock_components/GenericSystem`, другие плагины.

## Что сделано хорошо

Стоит явно отметить и позитивные решения: явная отправка стоп-пакета в
`on_deactivate` и в деструкторе (последний рубеж на случай `SIGINT`,
`guide_robot_system.cpp:161-170`), симметричный `on_cleanup`/`on_configure`
для избежания лишних переоткрытий порта, throttled-логирование
(`RCLCPP_*_THROTTLE`) вместо спама на каждый цикл, и сторожевой таймер с
гистерезисным логированием срабатывания/восстановления
(`guide_robot_system.cpp:926-952`) — теперь ещё и обязательный.

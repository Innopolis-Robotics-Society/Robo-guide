# Отчёт 2026-09-25: два лидара, сброс USB-хаба, запуск стека

## Итог

Оба лидара работают одновременно, стек поднимается кнопкой «Запустить» в guide-launcher.
Проверено на роботе запуском `start_stack.sh` без аргументов: `sllidar_left` (S/N `42B6…`) и
`sllidar_right` (S/N `B7B4…`) оба `health OK`, supervisor `BRINGUP -> ACTIVE`, активны 8 групп,
launcher `UP`, ошибок в логе нет.

## Что было сломано и почему

- Лидары и микрофон (XVF3800) сидят на одном single-TT USB-хабе `1-2.1` (Terminus 1a40:0101).
  Открытие и закрытие CP210x на нём даёт `-110`, `cp210x_open - Unable to enable UART`,
  в sllidar `code 80008004`.
- Причина, которую я сначала не видел: `usb_serial_preflight` сам открывает и закрывает порты
  и после сброса хаба снова его вешает.
- Первый правый переходник (CP2102, serial `0001`) оказался неисправным. Заменён на CH340.
- Новый CH340 сначала занимал имя `tty_sonar` из-за старого udev-правила сонара «через хаб».
- Отдельно: сбой LLM был на стороне Selectel (503 `upstream_unavailable`), IPv6 на роботе не
  маршрутизируется, Wi-Fi/hotspot нестабилен.

## Что сделано (все коммиты запушены в `dev`, робот обновлён)

| Коммит | Суть |
|---|---|
| ff2d51b, fd7dc84, 282e864 | Режим одного лидара `right_lidar:=false` (NaN-бланкинг сектора, supervisor не ждёт `/scan_right`, preflight не открывает правый порт, respawn левого лидара) |
| daba556 | udev: правый лидар на CH340 по порту хаба `1-2.1.4` → `tty_lidar_right`; правило сонара сужено; `right_lidar` снова `true` по умолчанию |
| 9dba5d8 | `start_stack.sh` сбрасывает хаб `1-2.1`, ждёт 10 с и стартует с `usb_preflight:=false` |

Настройки `start_stack.sh`: `STACK_USB_HUB` (по умолчанию `1-2.1`, пусто — не сбрасывать),
`STACK_USB_SETTLE_S` (по умолчанию 10).

## Правила эксплуатации

1. Запускать стек через кнопку или `start_stack.sh`. При ручном `ros2 launch … hardware.launch.py`
   сначала сбросить хаб, затем запускать с `usb_preflight:=false`.
2. Правый лидар должен стоять именно в порту `1-2.1.4` (у CH340 нет серийника, имя по порту).
3. Не открывать лидарные порты посторонними процессами при работающем стеке: это вешает хаб.
4. Восстановление вручную: `python3 guide_robot_bringup/guide_robot_bringup/usb_serial_preflight.py --reset-usb 1-2.1`,
   пауза около 10 с.
5. README bringup требует не ставить два лидара на один внешний хаб. Текущая раскладка это
   нарушает и держится на сбросе хаба. Надёжное решение — разнести лидары по разным хабам/портам
   хоста.

## Не проверено

- Реальная езда с двумя лидарами.
- Частота `/scan` под нагрузкой (load 21–34 на 6 ядер при старте, CLI не показал данные).
- Начальный yaw π в AMCL у входа Технопарка.
- Доступность Selectel LLM после сбоя.
- Перезапуск стека путями, не использующими `start_stack.sh` (docker restart и т. п.): хаб может
  повиснуть снова.
- Два старых падающих теста `guide_robot_semantic_map` (5 остановок expo_one), не связаны.
- Левый CP2102 продолжает логировать `-110` при open/close (шум).
- ~22 несохранённых файла пользователя не тронуты.

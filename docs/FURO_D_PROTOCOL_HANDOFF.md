Актуальность: 31 октября 2026 года. Рабочий проект:
`/home/legion/Projects/Robo-guide`.

Документ предназначен следующему разработчику или AI-агенту. Здесь собраны
пути к оригинальному Windows-софту, результаты реверса, проверенные пакеты,

## 1. Самое важное

- Робот — **FutureRobot FURO-D**, примерно 2015 года. В оригинальном
  FutureRobot выбран **`FuroD1.1`**. В DynRobot его ветка называется **`FURO`**.
  `FURO_S`, SISI, MASHA и прочие модели из того же EXE к этому роботу не относятся.
- Пользователь уже написал работающий ROS 2 стек. **Колёсное управление
  работает хорошо**; менять его калибровки, знаки и перестановки без причины не нужно.
- Контроллер общий для двух колёсных моторов и головы. ROS пока управляет
  только колёсами. Голова ещё не интегрирована.
- На компьютере робота подключение идёт через **USB–DB9 COM-адаптер**.
  Пины UART Jetson не используются.
- **Позиционная команда головы найдена** в оригинальном FutureRobot и
  независимо в native-коде DynRobot: `FF FF FE 09 83 1E 04 2B … CHK`.
- **Третье поле телеметрии — энкодер головы**, по прямому уточнению владельца.
  Первые два поля — позиции моторов колёс.
- Лог снят с **неподвижной головой**. Диапазон 1747–1775 — колебания
  показаний в неподвижном состоянии, а не диапазон поворота.
- В логе **нет команд движения головы или колёс**. Там запрос телеметрии
  и ответы. Команду головы восстановили из программ, а не угадали по логу.
- **Аппаратных проверок новых команд ещё не выполнено.** Исходящие пакеты
  получены перехватом событий оригинальной DLL без COM-порта.
- Установленный вычислитель проверен как **Jetson Orin Nano**, aarch64,
  Python 3.10.12. Владелец ранее называл его Xavier; для подключения
  ориентироваться на фактические сведения с хоста.

## 5. Общий формат пакетов FF FF

Для подтверждённых пакетов:

```text
FF FF ID LEN INSTRUCTION PARAMS... CHECKSUM
```

- Общая длина: `LEN + 4` байт.
- `CHECKSUM = (~sum(packet[2:-1])) & 0xFF`.
- Сумма всех байтов начиная с ID, включая checksum, по модулю 256 равна `FF`.
- Многобайтовые поля в исследованных командах — little-endian.
- Передавать **бинарные байты**, не текстовую строку с hex.
- `FE` используется как broadcast в командах; `2E` встречается как ID платы
  в телеметрии и запросе режима энкодеров.

Не считать всю реализацию стандартным Dynamixel: есть проприетарная
инструкция FURO `06`, особые регистры, а в библиотеке есть и совсем другой
формат с заголовком `55`.

## 6. Управление колёсами: совместимость с ROS подтверждена

Рабочий пакет `GuideRobotSystem::writeSpeedPacket`:

```text
FF FF FE 0E 06 20 04
2E V1_LO V1_HI A1_LO A1_HI
2F V2_LO V2_HI A2_LO A2_HI
CHK
```

Всего 18 байт. Скорости — int16 LE. В текущем конфиге дополнительные поля
обоих слотов равны 1000, то есть `E8 03`.

**Побайтно сопоставлено с оригинальным
`MobilityJoveTech.DriveDifferential(leftVelocity, leftTime, rightVelocity, rightTime)`.**
Для слотов 123 и -321 при дополнительных полях 1000:

```text
FF FF FE 0E 06 20 04 2E 7B 00 E8 03 2F BF FE E8 03 5E
```

Для обоих нулевых слотов:

```text
FF FF FE 0E 06 20 04 2E 00 00 E8 03 2F 00 00 E8 03 96
```

Артефакты: `analysis/CaptureWheels.cs`, `analysis/wheel_packets.txt`.

Нюансы:

- Оригинальный метод кладёт аргумент rightVelocity в первый слот `2E`,
  leftVelocity — во второй `2F`. Не подменять фактический порядок слотов
  названиями аргументов. В ROS знаки и перестановка уже проверены ездой.
- В ROS дополнительное поле названо `motor_accel`, в оригинальном API — Time;
  DynRobot отправляет туда фиксированные 1000. Совпадение байтов подтверждено,
  **точное физическое значение и единицы поля этим не доказаны**.
- В ROS есть собственное преобразование скоростей с экспериментальной
  калибровкой. Не заменять его старым коэффициентом DynRobot.

## 7. Голова: найденная позиционная команда

```text
FF FF FE 09 83 1E 04 2B PL PH VL VH CHK
```

| Поле | Назначение |
| --- | --- |
| `FE` | broadcast пакета |
| `09` | длина; всего 13 байт |
| `83` | позиционная Sync Write |
| `1E` | начальный регистр позиции |
| `04` | четыре байта данных на ось |
| `2B` | адрес позиционной оси головы, decimal 43 |
| `PL PH` | абсолютная позиция uint16 LE |
| `VL VH` | скорость uint16 LE |
| `CHK` | инвертированная сумма |

**Это абсолютная позиция, а не относительный инкремент и не знаковая
колёсная скорость. Для головы — `83 1E`, для колёс — `06 20`.**

Перехваченные примеры:

```text
position=1900, speed=10:
FF FF FE 09 83 1E 04 2B 6C 07 0A 00 AB

position=1800, speed=10:
FF FF FE 09 83 1E 04 2B 08 07 0A 00 0F

position=2000, speed=10:
FF FF FE 09 83 1E 04 2B D0 07 0A 00 47
```

Эти примеры — спецификация формата, **не готовый сценарий отправки в робота**.
Нельзя считать 1900 измеренным текущим центром и автоматически отправлять его
при старте: это лишь значение из сохранённого DynRobot-конфига.

### Цепочка в FutureRobot

```text
FuroD1_1.SetHeadYaw(angle_deg, speed_deg_s)
  -> ServoActuator.SetVelocity(speed_deg_s)
  -> ServoActuatorHeadYawByFuroD.SetPosition(-angle_deg)
  -> MobilityJoveTech.DriveOneAxis(0x2B, raw_position, raw_speed)
```

`ServoActuatorHeadYawByFuroD`:

- `deviceID = 0x2B`;
- `limitID = 0x28`;
- калибровка читается как `BodyPoseLimit.waistPitch`;
- угол масштабируется по тройке min/center/max из контроллера;
- при отсутствующих/нулевых лимитах метод может не отправить движение.

**Важно про `-35 / 0 / +35°`.** Эти числа лежат в конструкторе класса
(`ldc.i4.s 0xffffffdd` = -35, `0x23` = +35) и являются дефолтом **общей
библиотеки**. `ServoActuatorHeadYawByFuroD` переопределяет их из
`BodyPoseLimit.waistPitch`, прочитанного с контроллера (`ReadPositionLimit`),
поэтому в работе действует не -35/+35, а то, что ответила плата.

Для **FURO-D** реальный программный предел — **±15°**, из профиля
`ssd/DynRobot/configs/furo-d/config.txt`:

```text
FURO_ROBOT_HEAD_COEFFICIENT = 8.7266e-4
FURO_HEAD_ZERO            = 1900
FURO_MAX_HEAD_ANGLE       = 15.0
```

DynPult независимо подтверждает ту же конфигурацию одной осью:
`head=1`, `headAxis=2`, `headDeltas=1` в `ssd/DynPult/dynpult.ini`.

**У головы FURO-D одна степень свободы — только поворот (влево/вправо).**
Питча, ролла и лифта у неё нет. Имена `ServoActuatorHeadPitch`,
`ServoActuatorHeadYaw` (адрес `27`), `MashaHeadLuft` и т. п. — это классы
общей библиотеки для других моделей линейки (MASHA, NASTYA, VALERIA, SISI);
к FURO-D они не относятся и как источник истины для нашего робота не годятся.

**Название `waist`/`waistPitch` здесь используется для канала поворота головы
FURO-D.** Это имя поля из общей библиотеки, а не признак второй оси.

### Масштаб головы FURO-D считается из конфига

```text
coef = 8.7266e-4 рад/ед  ->  0.05 град/ед  ->  20 ед/градус
raw  = trunc(angle_rad / coef) + FURO_HEAD_ZERO
```

| угол | raw |
| ---: | ---: |
| -15° | 1600 |
| -10° | 1700 |
| -5° | 1800 |
| 0° | 1900 |
| +5° | 2000 |
| +10° | 2100 |
| +15° | 2200 |

Отсюда же берётся ответ на вопрос из §17: энкодер головы в логе колебался
`1747…1775`, то есть **−153…−125 ед от нуля = −7.7…−6.3°**. Голова стояла
несколько градусов левее нуля, а размах 28 единиц — 1.4°, то есть дрожание
неподвижного датчика. Это не диапазон поворота.

Внимание: 1900 — это `FURO_HEAD_ZERO` из конфига DynRobot, то есть
**калиброванный ноль конкретной установки**, а не измеренный центр. Перед
первой отправкой команды его надо подтвердить чтением `RequestLimit(0x28)`,
а не считать гарантированным.

Преобразование скорости базовым `ServoActuator.SetVelocity`:

```text
raw_speed = trunc(1.2 * clamp(deg_per_sec, 0, 120) * 4096 / 240 / 100)
```

50°/с из оригинальных кнопок дают raw 10. Семантика raw 0 в прошивке не установлена.

### Независимое подтверждение из DynRobot

В `analysis/dynrobot.asm`, для текущего `ssd/DynRobot/dynrobot.exe`:

- `0x458F00`: ограничение угла и вычисление
  `raw = trunc(angle_rad / FURO_ROBOT_HEAD_COEFFICIENT) + FURO_HEAD_ZERO`;
- `0x4592E0`: сборка того же 13-байтового пакета, скорость жёстко равна 10;
- `0x458EE0`: обратный пересчёт последней отправленной позиции.

По сохранённому конфигу около 20 raw единиц соответствуют градусу;
±15° дают приблизительно raw 1600–2200, центр 1900.

Однако:

1. Это шкала **задаваемой позиции**; её совпадение со шкалой энкодера не проверено.
2. Знак DynRobot не нужно автоматически считать знаком FutureRobot:
   `FuroD1_1.SetHeadYaw` инвертирует угол.
3. Возвращаемое DynRobot значение по адресу `0x458EE0` использует
   **последнюю команду**, а не доказывает чтение реального энкодера.
4. -35…+35° в API FutureRobot и ±15° в DynRobot — разные программные
   ограничения. Физический диапазон пока не измерен.

### Гипотеза о «мёртвой зоне»

В DynRobot найдены программные причины задержек:

- сравнение изменения угла с **0.005 рад**, примерно 0.286° / 6 raw единиц;
- после отправки устанавливается таймер **4000 мс**, который может задерживать
  малые последующие изменения;
- опциональный `FURO_USE_SMOOTH_HEAD_CONTROL` разбивает перемещение на шаги
  до 60 raw единиц с интервалом более 500 мс; в коде дефолт выключен.

Это **не доказательство порога прошивки, механического люфта или статического
трения**. Воспоминание коллеги о больших инкрементах не должно превращаться
в основание сразу посылать большое перемещение.

## 8. Телеметрия: три энкодерных поля

Запрос из реального лога:

```text
FF FF 2E 04 03 A0 05 25
```

В DLL он называется `MobilityJoveTech.SetEncoderType(5)`.
В текущем ROS используется тот же запрос.

Ответ — 19 байт:

```text
offset  size  содержимое
0       2     FF FF
2       1     2E
3       1     0F
4       1     47
5       1     A0
6       4     энкодер колёсного слота 1, LE
10      4     энкодер колёсного слота 2, LE
14      4     энкодер головы, LE
18      1     checksum
```

Для анализа все три поля декодированы как int32. Для колёс signed int32
подтверждается оригинальным `GetEncoderData`. Для головы реальные значения
положительные; разрядность физического датчика и поведение на переполнении
отдельно не исследованы. Сырой hex надо сохранять для переинтерпретации.

### Что именно есть в logs5(1).html

Оригинал в Downloads ноутбука:

```text
/home/legion/Downloads/logs5(1).html
```

Копия:

```text
/home/legion/Robot-recovery/furo-2015/logs/logs5(1).html
```

Процесс в записи: `C:\FutureRobot--\FuroSoftware\FutureRobot.FuroManager.exe`,
COM3, 115200, 8N1. Дата внутри записи — 22 июля 2026 года.

- 6943 строки событий монитора.
- 87 непустых `IRP_MJ_WRITE/DOWN`, все содержат один запрос `A0 05` выше.
- 87 соответствующих WRITE/UP — подтверждения завершения тех же операций,
  **не дополнительные отправки**.
- 384 непустых READ/UP дают **429 кадров** после склейки потока.
- Все 429 кадров имеют заголовок `FF FF 2E 0F 47 A0`, длину 19 и верную checksum.

| Колёсный слот 2 | -4150 | 4324 |
| Энкодер головы | 1747 | 1775 |

Владелец подтвердил **назначение третьего поля** и **отсутствие вращения головы**.
Поэтому нельзя вычислять угловой масштаб по размаху 28 или считать его
механическим диапазоном. Причина колебаний неподвижного энкодера ещё не измерена.

Первоначальное воспоминание коллеги: показания порядка ±2000 и возможная
мёртвая зона. По числам ±2000 хорошо согласуется с колёсным полем 2;
назначение данных нужно брать из уточнения владельца, а не из этого воспоминания.

Оригинальный `GetPositionData` головы ожидает иной формат ответа, а в DLL
также есть разбор `A0` как x/y/theta. Не переносить эти альтернативные
интерпретации на наблюдаемый режим 5: для него назначение трёх полей известно.

## 9. Чтение версии, состояния, лимитов и коэффициентов

Перехвачено оригинальной DLL без подключения к железу:

| Вызов | Пакет |
| --- | --- |
| `QueryVersion()` | `FF FF FE 03 02 00 FC` |
| `QueryMotorState()` | `FF FF FE 03 02 A4 58` |
| `RequestLimit(0x28)` | `FF FF FE 04 02 B1 28 22` |
| `RequestGain(0x28)` | `FF FF FE 04 02 B2 28 21` |
| `SetEncoderType(0)` | `FF FF 2E 04 03 A0 00 2A` |
| `SetEncoderType(5)` | `FF FF 2E 04 03 A0 05 25` |

Checksum и длина этих шести пакетов проверены. **На установленном контроллере
пока подтверждён только режим 5 из существующего лога.**

Ожидания парсеров:

- `GetVersion`: 10-байтовый кадр, три байта версии начиная с offset 6.
- `GetOperationState`: 11 байт, ID `2E`, `A4` по offset 5,
  четыре сырых байта по offset 6–9. Значения битов не расшифрованы.
- `GetPositionLimit`: 14 байт, ID `2E`, LEN `0A`, `B1` по offset 5,
  selector `28` по offset 6, min/center/max uint16 LE по offset 7, 9, 11.
- `GetBodyGain`: ответ `B2`, коэффициенты позиционной оси сохраняются
  в `BodyPoseGain.waistPitch` как uint32. Перед реализацией перечитать метод целиком.

Запросы/ответы этих типов отсутствуют в предоставленном COM-логе.
Не называть четыре байта A4 током/температурой/ошибками без проверки.

## 10. Снятие тока с колёс: кандидат, не подтверждённая функция платы

Владелец наблюдает: после подачи питания колёсные моторы свободны;
после запуска текущего ROS появляется удержание. ROS головой не управляет.

В штатной панели `FormFuroSTester`:

- `checkBoxMobileLeftEnable` вызывает `ServoPower(1, 1/0)`;
- `checkBoxMobileRightEnable` — `ServoPower(2, 1/0)`;
- `checkBoxWaistEnable` — `ServoPower(3, 2/0)` для канала головы.

Перехват `MobilityJoveTech.ServoPower`:

```text
Левый колёсный, off:    55 01 83 00 00 00 00
Правый колёсный, off:   55 02 83 00 00 00 00
Левый колёсный, on:     55 01 83 FE 00 00 00
Правый колёсный, on:    55 02 83 FE 00 00 00

Канал головы, off:      55 03 83 00 00 00 00
Канал головы, on mode2: 55 03 83 08 00 00 00
```

Важно:

- Это **другой семибайтовый формат с заголовком `55`**, без checksum FF FF-семейства.
- `1/2/3` здесь номера каналов ServoPower, не адреса `2E/2F/2B` позиционных пакетов.
- Совместимость работающего `FF FF … 06 20` не доказывает поддержку `55 …`.
- Название метода и выключатели подтверждены, **реальное снятие тока
  на этой плате не проверено**. Не выдавать эти байты за гарантированно рабочую команду.
- В ROS и скрипт записи эти команды не добавлены.
- В текущем ROS отдельной команды enable/disable нет; он начинает отправлять
  скорости и при остановке отправляет нулевую скорость. Версия, что первая
  команда скорости включает силовую часть, пока гипотеза. Эффект открытия
  COM и запроса телеметрии ещё нужно отделить экспериментом.
- Нулевая скорость сама по себе не является подтверждённым torque-off.
- **Проверено по IL:** `MobilityJoveTech::StopWheel` = `isWheelRunning = false`,
  затем `DriveWheel(0.0, 0.0)`, затем `Dispose` таймера. **Отдельной команды
  торможения или снятия момента в библиотеке нет.** Любая «остановка» в
  оригинальном ПО — это та же нулевая скорость. Совпадает с тем, что делает ROS.
- Команда аппаратного watchdog, таймаута по потере связи, чтения фактических
  моторных токов или гарантированного автоматического снятия тока пока не найдена.

## 11. Батарея и прочие полезные функции

### Напряжение батареи — конкретная цепочка для FuroD1.1

Конструктор `FuroD1_1` назначает `UltrasonicSRF_V20` одновременно как
`IUltrasonic` и **`IBattery`**. В `ultrasonicSensor_DataUpdated`
вызывается `GetBatteryVoltage()`, значение публикуется старым приложением
как событие `Battery`.

Парсер принимает STX, ASCII `BAT`, пять символов числа и ETX:

```text
02 42 41 54 32 34 2E 35 30 03
   B  A  T  2  4  .  5  0
```

Синтетический кадр `STX BAT24.50 ETX` через оригинальный `SetData`
даёт **24.5** в `GetBatteryVoltage()`. Это проверка парсера, не измерение робота.

Но текущий `guide_robot_sonar/src/sonar_driver.cpp` использует **другой протокол**:

```text
request:  CC (30 + sonar_id) XOR
response: CC id? distance_lo distance_hi XOR
```

Нужно сначала выяснить, выдаёт ли установленная плата ASCII BAT, поддерживает
ли оба формата либо имеет отдельный запрос батареи. Не добавлять выдуманный
запрос в COM. Возможный результат для ROS — `sensor_msgs/BatteryState.voltage`.
Процент заряда, ток, температура и ёмкость по этой цепочке не подтверждены.

### Второй протокол сонаров и что реально стоит на роботе

В библиотеке есть **две разные платы сонаров**, и это меняет картину:

| класс | протокол | кодировка |
| --- | --- | --- |
| `UltrasonicSRF_V20` | `FF FF` Dynamixel-подобный, ID `15`, `FNC_SENSING 0x90` | бинарная |
| `UltrasonicHagisonic` | ASCII в `STX`/`ETX` | десятичные цифры |

`NaviRobotFuroServoSonic.dll` (класс `ioFuroWare`, методы `GetSensor` и
`serialPortUltrasonic_DataReceived`) работает именно с **`UltrasonicHagisonic`**,
а не с SRF. Если на роботе стоит плата Hagisonic, то протокол `CC (30+id) XOR`
из текущего `sonar_driver.cpp` к ней не относится вообще.

Формат кадра Hagisonic (из `analysis/il/Devices.il`, `UltrasonicHagisonic::SetData`):

```text
STX  0x02
CMD  0x5e  (CMD_DATA)
idx  0x30 + sensor_index   (0..7)
SEP  0x7c  '|'
...digits...  ASCII decimal, БЕЗ ведущих нулей
ETX  0x03
```

Разбор: пара `STX 0x5e`, байт `idx`, байт `SEP`, цифры до `ETX`,
значение = накопленное `10*v + (byte - 0x30)`, затем **делится на 1000**
(то есть метры) и кладётся в слот по таблице:

| raw idx | слот | | raw idx | слот |
| ---: | ---: | --- | ---: | ---: |
| 0 | 8 | | 4 | 2 |
| 1 | 9 | | 5 | 4 |
| 2 | 0 | | 6 | 5 |
| 3 | 1 | | 7 | 6 |

Слотов в массиве **10**, а сырых индексов **8**: слоты **3 и 7 не пишутся
никогда**. Имена остальных констант: `CMD_SET 0x23`, `CMD_GET 0x40`,
`CMD_RTN 0x24`, `CMD_ACK 0x21`, `SENSOR_COUNT = 10`.

Граница проверки в IL — только `idx < 8`, нижней границы нет; при мусорном
индексе меньше `0x30` будет выход за пределы массива. Это баг старого кода,
а не свойство протокола.

Статус: **формат и раскладка доказаны по IL, но на этом роботе Hagisonic
никогда не наблюдался**. Что реально стоит и в каком режиме — мерять на месте,
до этого не менять `sonar_driver.cpp`.

### Статусы в общей библиотеке: ещё не доказательство датчиков FURO-D

`MobilityJoveTech.GetBoardData` распознаёт 11 байт:

```text
FF FF 2E 07 ?? 48 magneticLine batteryLevel chargingStatus bumperStatus CHK
```

Названия полей известны, но наличие работающих бамперов, магнитной линии
и статуса зарядки на данном роботе не доказано. В специфичном `FuroD1_1`
не найдена явная подписка на `BoardStatusUpdated`; батарея там подключена
через плату сонаров. Сначала нужен фактический ответ и изменение поля при
физическом событии. `batteryLevel` не объявлять процентами без шкалы.

### Настройки регуляторов

Есть чтение/запись позиционных коэффициентов и лимитов, а также PI-параметры
колёс через `A9`. Факт сохранения настроек в EEPROM/flash **не установлен**.

Найдены несогласованности самой старой DLL:

- `SetGain(true,1,2,3,4)` формирует
  `FF FF 2E 06 03 A9 01 02 03 04 15` — **11 байт при LEN=06**, тогда как
  остальные проверенные пакеты соблюдают `LEN + 4`. Checksum верна.
- `DriveDifferentialVelocityAcceleration` использует регистр `21`, но
  в исследованном коде первый слот получает rightVelocity в оба поля,
  а rightAcceleration не используется. Метод нельзя переносить по одному названию.

Не экспериментировать с коэффициентами хорошо работающих колёс ради
проверки существования API. Сначала чтение и резервирование значений.

### Что не является функцией прошивки

`MoveWheel(distance, velocity)` и `RotateWheel(angle, velocity)` в оригинале
реализованы через `System.Threading.Timer` на Windows: сравнение
перемещения, повторение команды скорости и отправка stop. Это **логика хоста**,
не доказательство автономного движения на заданное расстояние внутри платы.
ROS/Nav2 уже решает подобные задачи своим способом.

## 13. Версии FutureRobot и доверие к старому коду

`FutureRobot.Devices.dll`, `Robots.dll`, `Common.dll`, `UI.dll` — .NET-сборки,
поэтому IL содержит читаемые имена и пригоден для доказательства структуры пакета.
DynRobot/DynPult — native PE32: там использовались строки, адреса ссылок и
`objdump -d -Mintel`. Адреса в документе относятся к указанному EXE,
а не автоматически к `.orig.exe` или другой резервной версии.

### Ещё не разобранные направления

- `ssd/backup` и `DynRobot.7z`: сравнение дополнительных версий.
- Три `Desktop/Release*`: другой NaviRobot-софт, включая
  `NaviRobotFuroServoSonic.dll`, EXE и PDB; могут дать дополнительные подсказки.
- `DynPult`: сетевой протокол можно разбирать отдельно, но он не нужен для COM-ROS.
- Сопоставление `55`-ветки с документацией/моделью платы до любых отправок.
- Установленный сонарный протокол и наличие батарейного канала.

## 16. Порядок дальнейших аппаратных проверок и ограничения владельца

Владелец прямо просит исключить случайные команды, способные повредить
настройки или прошивку. **Не перебирать опкоды, регистры или ID, не делать
широковещательное сканирование, не посылать «похожие на Dynamixel» команды.**
Не считать неизвестный регистр безопасным для чтения или записи по аналогии.

Для первой сессии разрешённый технический набор ограничен:

1. Убедиться, что ROS не запущен, порт правильный и свободен.
2. После холодного включения зафиксировать, свободны ли колёса и голова.
3. Короткий `--passive`: ни одного исходящего байта. Проверить эффект открытия порта.
4. Только известный `FF FF 2E 04 03 A0 05 25` из реального лога.
5. Проверить неподвижные показания и отсутствие неожиданного удержания/движения.
6. Немного повернуть голову вручную, проверить изменение третьего поля.
7. Плавно снять left/right/center; не преодолевать удержание силой и не давить в упоры.
8. Сохранить данные, закрыть COM и скопировать результаты на ноутбук.

Человек должен быть рядом и иметь возможность снять питание приводов.
SSH, закрытие скрипта и нулевая скорость не заменяют подтверждённый способ
снять питание. Не запускать ROS параллельно со скриптом.

**Не включать в этот первый сеанс автоматически:** пакеты `55`, чтение
непроверенных регистров, запись коэффициентов/лимитов, смену режимов платы,
позиционные команды головы, сбросы или загрузчик. Всё это отдельные опыты
с конкретно изученным пакетом и понятной привязкой к данной плате.

Даже наличие пакета в DLL не равно гарантии отсутствия побочного эффекта
на другой версии прошивки. В первой проверке опираемся на пакет,
который уже есть в реальном обмене именно этого робота.

## 17. Что действительно осталось выяснить

Уже выяснено офлайн (не требует робота):

- масштаб головы: `8.7266e-4` рад/ед = 20 ед/градус, ноль 1900, предел ±15°;
- у головы FURO-D одна ось — только поворот; питча/ролла/лифта нет;
- `StopWheel` — это `DriveWheel(0,0)` плюс dispose таймера, отдельной
  команды торможения в библиотеке нет;
- `ServoActuator.Init()` = `SetPosition(midAngle)`, так что инициализация
  головы — это просто выезд в центр;
- второй протокол сонаров: Hagisonic (см. раздел 11),
- в логе голова стояла на −153…−125 ед от нуля (−7.7…−6.3°), размах 28 ед = 1.4° дрожания.

Осталось измерить (только с включённым роботом):

- физический угол поворота и совпадает ли он с ±15° программного предела;
- повторяемость проходов и реальный центр энкодера на этой установке;
  конфиг говорит 1900, но это калиброванный ноль, а не измерение;
- согласован ли знак энкодера со знаком команды (`SetHeadYaw` инвертирует угол);
- какая операция включает удержание колёс: открытие порта, запрос или первая скорость;
- поддерживает ли плата ServoPower формата `55`;
- отвечают ли версия/A4/B1/B2 и как трактовать реальные ответы;
- доступно ли напряжение батареи через установленную плату сонаров (SRF или Hagisonic);
- есть ли реальные бамперы/статус зарядки, а не только поля общего API;
- существуют ли аппаратный таймаут, диагностика токов/температур и образы MCU
  в дополнительных материалах; пока они не найдены.

# План теста головы FURO-D на реальном железе

Актуальность: 31 октября 2026. Составлен после офлайн-реверса
(`docs/FURO_D_PROTOCOL_HANDOFF.md`), но **до** первой подачи команд голове.

Задача: измерить физику головы и проверить, совпадает ли наш масштаб
с реальностью. Ничего в прошивке и параметрах контроллера не меняем.

---

## 0. Что уже известно офлайн (не перепроверять на железе)

Из `ssd/DynRobot/configs/furo-d/config.txt`:

```text
FURO_ROBOT_HEAD_COEFFICIENT = 8.7266e-4   # рад/ед -> 0.05°/ед -> 20 ед/градус
FURO_HEAD_ZERO            = 1900          # калиброванный ноль
FURO_MAX_HEAD_ANGLE       = 15.0          # программный предел, ±15°
```

Из `ssd/DynPult/dynpult.ini`: `head=1`, `headAxis=2`, `headDeltas=1` —
одна ось, дельтовый режим.

Пакет позиции (подтверждён в IL FutureRobot и в native DynRobot):

```text
FF FF FE 09 83 1E 04 2B PL PH VL VH CHK
```

| угол | ожидаемый raw |
| ---: | ---: |
| −15° | 1600 |
| −10° | 1700 |
| −5° | 1800 |
| 0° | 1900 |
| +5° | 2000 |
| +10° | 2100 |
| +15° | 2200 |

`StopWheel` = `DriveWheel(0,0)`; отдельной команды торможения нет.
`ServoActuator.Init()` = `SetPosition(midAngle)`.

---

## 1. Что даёт тест (и что не даёт)

**Проверяем:**

1. работает ли запрос энкодера на этой плате;
2. реальный центр энкодера против конфигурного 1900;
3. знак энкодера против знака команды;
4. физический угол на 5/10/15° и совпадает ли он с 20 ед/градус;
5. шум и повторяемость в неподвижном состоянии;
6. где реально кончается механический ход.

**Не проверяем в этом сеансе:**

- команды `55` (ServoPower), включение/снятие тока;
- чтение/запись коэффициентов, лимитов, версий, `A4`;
- смену режима энкодера, сбросы, загрузчик;
- батарею и сонары;
- что-либо в прошивке контроллера.

Причина: всё это отдельные опыты, и каждый требует своего разбора последствий.

---

## 2. Оборудование и безопасность

- Робот устойчиво стоит, колёса на полу, вокруг головы ≥40 см свободного места.
- Человек рядом держит руку на **физическом питании приводов**. Закрытие SSH,
  Ctrl+C и нулевая скорость — **не** подтверждённый способ обесточить моторы.
- Порт `/dev/tty_motors` → USB–DB9 адаптер. Прямые UART Jetson не используются.
- Энкодеры читаются с частотой 5 Гц (200 мс), это безопасно и уже проверено тестом.

## 3. Подготовка (5 минут, до подачи питания на приводы)

### 3.1 Убедиться, что ROS не держит порт

```bash
pgrep -af "ros2|_node|controller_server|guide_robot" | head
ls -l /dev/tty_motors
fuser -v /dev/tty_motors 2>&1 || echo "порт свободен"
```

Ожидаемо: процессов стека нет, порт свободен. Если стек запущен — **остановить
через меню оператора**, не через `kill`, и дождаться выхода.

> Блокировка TIOCEXCL не спасает от процесса, открывшего порт раньше нас,
> поэтому проверяем именно `fuser`, а не только свои ощущения.

### 3.2 Скопировать на робота ровно один файл

```bash
scp scripts/furo_head_capture.py jetson@10.42.0.2:~/furo_head_capture.py
```

Скрипт содержит **одно** место записи в COM и **один** фиксированный пакет
`FF FF 2E 04 03 A0 05 25` (87 раз присутствует в исходном логе). Ввода
произвольного hex, выбора регистра, команд движения и записи настроек в нём нет.

### 3.3 Проверить, что порт отвечает вообще

```bash
ssh jetson@10.42.0.2
python3 ~/furo_head_capture.py --passive --duration 3 \
  --output ~/head-t0-passive
cat ~/head-t0-passive/summary.json
```

Пассивный режим **не отправляет ни одного байта**. Смотреть на два поля:
`commands_sent` (обязано быть `0`) и `frames` (может быть `0` — контроллер
молчит без опроса, это нормально).

**Отдельно отметить руками:** изменилось ли удержание от самого открытия COM.
USB-адаптер может дёргать управляющие линии при open/close. Это ответ на
вопрос из §17 хендоффа — что именно включает удержание.

## 4. Шаг 1. Чтение энкодеров без движения

```bash
python3 ~/furo_head_capture.py --duration 20 \
  --output ~/head-t1-idle
```

Что проверить в `summary.json`:

| поле | ожидание |
| --- | --- |
| `frames` | > 0, растёт |
| `bad_checksums` | `0` |
| `discarded_bytes`, `trailing_bytes` | `0` |
| `head_min` / `head_max` | узкий размах, сотни единиц, не тысячи |
| `status` | `finished` |

**Стоп-условие:** появилось удержание головы, которого не было до запуска,
или голова дёрнулась → остановиться, сохранить `summary.json`, дальше не идти.

Проверить руками: колёса не крутятся, голова не двигается, энкодеры колёс
стоят на месте (в CSV `wheel_slot_1`, `wheel_slot_2` почти константа).

## 5. Шаг 2. Ноль, знак и масштаб энкодера (ручной)

Голову двигаем **только руками**, без единой команды движения.

```bash
python3 ~/furo_head_capture.py --duration 0 \
  --output ~/head-t2-manual
```

Скрипт принимает `l` / `r` / `c` + Enter и снимает медиану последнего окна
(5 кадров ≈ 1 с). Порядок:

1. Поставить голову **прямо** (на глаз) → `c` + Enter.
2. Плавно повернуть **до левого упора**, без нажима → `l` + Enter.
3. Плавно до **правого упора** → `r` + Enter.
4. Вернуться в центр, снова `c`.
5. **Повторить весь проход** ещё раз для оценки повторяемости.
6. `q` + Enter.

> Если голова **сопротивляется**, не преодолевать удержание силой и не искать
> наугад torque-off. Зафиксировать факт сопротивления и остановить опыт.

Скрипт сам посчитает в `summary.json`:

```json
"endpoints": { "left": ..., "right": ..., "span": ...,
               "midpoint": ..., "increases_toward": "left|right" }
```

### Как читать результат

Сравнить с ожиданием `1600 … 2200`:

- **`span` ≈ 600** → масштаб подтверждён, 20 ед/градус верны.
- **`span` заметно меньше** → механический ход уже программного ±15°;
  это важный факт, его нельзя игнорировать при первой команде.
- **`span` заметно больше** → наш `FURO_MAX_HEAD_ANGLE` консервативен.
- **`midpoint` далеко от 1900** → калиброванный ноль в конфиге не совпадает
  с этой установкой; именно `midpoint`, а не 1900, брать за центр.
- Расхождение между двумя проходами = **повторяемость**. Больше ~50 ед
  (2.5°) — энкодер или механика шумит, команды позиции надо ставить осторожно.

`increases_toward` даёт **знак**: если рост идёт к левому упору, а
`SetHeadYaw` инвертирует угол (`neg`), то знаки команды и энкодера
противоположны — это надо явно записать, а не выводить по ходу дела.

## 6. Шаг 3. Первая одиночная команда — только если шаг 2 сошёлся

**Предусловие:** `span` и `midpoint` получены, обе половины прохода
устойчивы, ничего не сопротивлялось.

### 6.1 Сгенерировать пакет офлайн

Генератор **никогда не открывает порт**, только печатает байты:

```bash
# на ноутбуке
python3 scripts/furo_head_packet.py --angle 3 --center <midpoint>
python3 scripts/furo_head_packet.py --position <midpoint> --speed 10
```

Начать с **±3°**, а не с 15°. Это 60 ед — заведомо внутри найденного хода,
и мелкая ошибка знака не приведёт к удару в упор.

### 6.2 Отправить одну команду и сразу прочитать энкодер

Отдельного «отправить и прочитать» в capture-скрипте **нет** намеренно.
Поэтому порядок такой:

1. Запустить capture в фоне (`--duration 30`), чтобы шёл лог энкодера.
2. Из второй SSH-сессии отправить **ровно один** пакет через `--binary`:

   ```bash
   python3 scripts/furo_head_packet.py --angle 3 --center <midpoint> --binary \
     > /tmp/head3.bin
   # передать в порт (порт должен быть свободен от capture!)
   ```

   > Сначала сверить содержимое `xxd /tmp/head3.bin` с ожидаемым hex.
   > Checksum, длину 13 и поле `2B` проверить **глазами** до отправки.

3. Остановить capture, открыть CSV, посмотреть, куда ушёл энкодер.

**Стоп-условие:** голова пошла не туда, или в упор, или энкодер не изменился
→ питание приводов, разбор записанного обмена, **дальше не подбирать**.
Помнить: capture и отправка не могут работать одновременно — порт один.

### 6.3 Если ±3° сработало

Повторить по одному шагу: `−3°`, `+5°`, `−5°`. Сверить измеренный угол
с ожидаемым (5° × 20 = 100 ед). Только потом пробовать `±10°`.
`±15°` — в самом конце, и только если `span` это позволяет.

Мелкие шаги **нарочно**: масштаб может оказаться другим, а упор — ближе.

## 7. Сбор результатов

```bash
# на роботе
tar czf ~/furo-head-$(date +%Y%m%d-%H%M%S).tgz ~/head-t*

# на ноутбуке
scp jetson@10.42.0.2:~/furo-head-*.tgz .
```

Сохранять **сырой hex** (`frames.csv`, `frame_hex`), а не только медианы:
если окажется, что третье поле — не то, что мы думаем, данные можно
переинтерпретировать только по сырым байтам.

## 8. Критерии успеха и провала

| результат | вывод |
| --- | --- |
| `frames > 0`, `bad_checksums = 0`, `head` стабилен | запрос подтверждён на этой плате |
| `span` ≈ 600 | масштаб 20 ед/градус подтверждён |
| `span` ≠ 600, но стабилен | масштаб другой — **не** подгонять, измерить и записать |
| `frames = 0` после всех запросов | плата не отвечает на этот запрос; нужен отдельный разбор |
| голова сопротивляется руками | удержание включено; это ответ на §17, а не помеха |
| отправка ±3° не изменила энкодер | команда не принята: разбирать пакет, не масштаб |
| энкодер поехал, а голова нет | команда принята, но механика/режим не тот |

---

## 9. Чего в этом плане сознательно нет

- Команд `55` и любого управления током.
- Чтения версии, `A4`, `B1`, `B2` — сначала пусть ответит то, что уже
  подтверждено логом.
- Записи коэффициентов и лимитов: колёса работают хорошо, трогать нельзя
  без резервирования.
- Автоматического перебора ID, регистров и опкодов.
- Совмещения с проверкой сонаров и батареи — другой сеанс, другой порт.

---

## 10. Если робот так и не появится в сети

Тест требует живого робота и `/dev/tty_motors`. Пока его нет, офлайновая
часть закрыта: масштаб, ноль, предел и пакет известны из конфигов и IL.
Единственное, что нельзя получить офлайн, — совпадение шкалы команды
со шкалой реального энкодера. Это и есть цель сеанса.

## 2. Протокол шины моторов (подтверждён)

Формат кадра:

```
FF FF <ID> <LEN> <INSTR> <REG> [params...] <CHK>
```

- `LEN` — количество байт **после** поля LEN: `INSTR + REG + params + CHK`.
- Полная длина кадра = `LEN + 4`.
- `CHK = ~sum(байты от ID до последнего параметра) & 0xFF`.
- Проверка: `sum(всех байт от ID до CHK) & 0xFF == 0xFF`.

Генератор проверен на эталонном запросе телеметрии: кадр
`FF FF 2E 04 03 A0 05 25` воспроизведён байт в байт.

### 2.1 Команда положения головы

```
FF FF FE 09 83 1E 04 2B <pos_lo> <pos_hi> <spd_lo> <spd_hi> <CHK>
```

`ID = 0xFE` (широковещательный), `INSTR = 0x83`, `REG = 0x1E`, первый параметр
`0x04`, второй `0x2B` (идентификатор оси головы), далее позиция uint16 LE и
скорость uint16 LE.

Проверенный пример: позиция 1770, скорость 10 →

```
FF FF FE 09 83 1E 04 2B EA 06 0A 00 2E
```

### 2.2 Чтение лимитов оси

Из декомпила `ControlBoardJoveTech::RequestLimit` (`analysis/il/Devices.il`,
строки 1677–1740): байты `255, 255, 254, 4, 2, 177, <partId>, <chk>`.
177 = `0xB1`, инструкция `0x02`.

```
FF FF FE 04 02 B1 <partId> <CHK>
```

Для оси головы `0x2B`: `FF FF FE 04 02 B1 2B 1F`.

**Ответ получен один раз**, кадр целиком:

```
ff ff 2e 0a 40 b1 2b 72 06 16 08 28 0a e3
```

Разбор: `LEN = 0x0A` (14 байт всего), `INSTR = 0x40`, `REG = 0xB1`,
`partId = 0x2B`, далее три uint16 LE:

| поле | hex | dec |
|---|---|---|
| min  | `72 06` | **1650** |
| init | `16 08` | **2070** |
| max  | `28 0A` | **2600** |

Контрольная сумма кадра проверена: `sum(байт со 2-го по 13-й) mod 256 = 255`.

Повторные запросы `0xB1` в этой сессии больше такого кадра не вернули — в
ответ шёл только поток телеметрии (см. 8.2).

### 2.3 Запись лимитов

Из декомпила `ControlBoardJoveTech::SetLimit` (`analysis/il/Devices.il`,
строки 1592–1673): байты `255, 255, 0x2F, 0x0A, 3, 177, <partId>`, далее три
uint16 LE (min, init, max), затем checksum по 14 байтам.

```
FF FF 2F 0A 03 B1 <partId> <min_lo> <min_hi> <init_lo> <init_hi> <max_lo> <max_hi> <CHK>
```

Собранные кадры:

```
текущие значения (для отката): FF FF 2F 0A 03 B1 2B 72 06 16 08 28 0A 1F
предлагаемые новые:            FF FF 2F 0A 03 B1 2B 50 05 EA 06 38 09 61
```

Второй кадр означает `min=1360, init=1770, max=2360`.

**Ни один из этих кадров не отправлялся.** Запись в контроллер не выполнялась
ни разу. Сохраняется ли значение после перезагрузки, принимает ли контроллер
команду и на какой адрес её реально надо слать — не проверено.

### 2.4 Телеметрия

Поток кадров по 19 байт:

```
ff ff 2e 0f 47 a0 c2 2c 00 00 21 e1 01 00 <HH> <LL> 00 00 <CHK>
```

Поле на смещении 14 (uint16 LE) — энкодер головы. Например `48 09` = 2376.
Соответствие поля голове установлено ранее сравнением с ручным перемещением
головы (см. 5.1); независимой сверки с другим источником положения не делалось.

## 5. Направление и геометрия

### 5.1 Направление

Установлено ранее визуальной проверкой (`--sign-test`, владелец смотрел на
голову): при `raw > 1770` голова уходит влево, при `raw < 1770` — вправо.
Отсюда в трекере `sign = -1`.

### 5.2 Что считается «прямо»

- Владелец вручную ставил голову «прямо» → энкодер ≈ **1770**. Владелец
  подтвердил это значение как «прямо».
- Голова, поставленная в **2082** (≈ `init` контроллера 2070), по словам
  владельца, **прямо не смотрит**.
- `FURO_HEAD_ZERO = 1900` из `configs/furo-d/config.txt` DynRobot — третье
  значение, ни с одним из измеренных не совпадает.

Какое из значений соответствует геометрической оси робота, не установлено.
Фактически используются два: 1770 (по слову владельца) и 2070 (`init` из
контроллера).

### 5.3 Масштаб

`FURO_ROBOT_HEAD_COEFFICIENT = 8.7266e-4` → 0.05°/единица → **20 единиц на
градус**. Взято из конфига, протрактором не проверялось. Согласуется с тем,
что цель 2000 от 1789 (211 единиц) дала смещение 222 единицы.

### 5.4 Итоговый ход при разных допущениях

| источник | диапазон | размах |
|---|---|---|
| контроллер (`min`/`max` из 2.2) | 1650 … 2600 | 950 ед = 47.5° |
| механика (рукой, 4.4) | 1305 … 2390 | 1085 ед = 54.3° |
| реально достигается командой (4.3) | 1674 … 2399 | 725 ед = 36.3° |
| от «прямо» 1770 вправо | до 1674 | 96 ед = **4.8°** |
| от «прямо» 1770 влево | до 2399 | 629 ед = **31.5°** |

## 6. Звук: reSpeaker XVF3800

### 6.1 Доступ

- USB `2886:001a`, ALSA card 0, интерфейс 3.
- На роботе нет `pyusb`, нет `xvf_host`, нет интернета. Чтение сделано через
  `USBDEVFS_CONTROL` ioctl из `ctypes`.
- `bmRequestType = 0xC0`, `bRequest = 0`, `wValue = 0x80 | cmdid`,
  `wIndex = resid`, `wLength = n + 1`.
- Байт 0 ответа — статус: `0` успех, `64` — повторить примерно через 15 мс.
- `DOA_VALUE`: resid 20, cmdid 18 → `<HH` = `(angle_deg, vad)`.
- `AEC_AZIMUTH_VALUES`: resid 33, cmdid 75 → 4 × float32, радианы.
- udev-правило `/etc/udev/rules.d/99-respeaker-xvf3800.rules`
  (`SUBSYSTEM=="usb", ATTR{idVendor}=="2886", ATTR{idProduct}=="001a", MODE="0666"`)
  установлено; DOA читается без sudo.

### 6.2 Калибровка

Измерено с владельцем, который вставал в известные позиции:

| положение владельца | DOA |
|---|---|
| перед роботом | 180…191° |
| правый бок робота | 91° |
| левый бок робота | 269° |

Плата установлена перевёрнутой, Type-C смотрит назад, ноль массива
перпендикулярен ребру платы. Принятое преобразование:

```
bearing = -(doa - 180)
```

### 6.3 Частота

Замер: 35 изменений DOA за 12 с, медианный интервал между изменениями 21 мс.
То есть DOA приходит пачками, а не строго периодически. Средняя частота
около 2.7 Гц (165 изменений за 61 с в другом замере).

## 7. Трекер головы

`scripts/sound_head_tracker.py`. Параметры по умолчанию:

```
zero=1770  units_per_deg=20  sign=-1  array_offset=180  mirror=-1
limit=15  min_step=3  deadband=2  stable=12  window=4
fov=90  curve=0.6  hold_s=0.28  cooldown=0.6  interval=0.04
raw_min=1335  raw_max=2360
```

Формула угла:

```
u = clamp(bearing / fov, -1, +1)
want_deg = limit * sign(u) * |u| ^ curve
```

При старте скрипт читает реальное положение головы через `QUERY`/`Decoder`,
нулевое положение не предполагается. `--dry-run` не пишет в порт,
`--sign-test` выполняет `+limit → 0 → -limit → 0`.

Замеренная задержка реакции: первая команда в лог через 0.78 с после старта,
соседние команды в логе через 0.12 с.

Проверенные живые отработки: `doa=128° → bearing +52° → голова +14.4° →
raw 1482`. Голова поворачивается **к** источнику звука.

Ограничение, не снятое: `/dev/tty_motors` держит ROS-нода
`guide_robot_system.cpp` (`serial_mutex_`). Пока стек запущен, трекер порт не
откроет (`Errno 16`). В продакшене команду голове должен слать сам узел.

## 8. Противоречия и непроверенное

### 8.1 Почему командой не достигается 1305, хотя рукой достигается

Данных достаточно для двух версий, различить их не удалось:

1. Программный предел: `min = 1650` прочитан из контроллера (2.2), а
   наблюдаемый минимум 1674 отличается от него на 24 единицы — примерно на
   величину минимального шага, который контроллер отрабатывает (4.2).
2. Механическое препятствие: ручной промер (4.4) делался раньше, до
   перезагрузок робота; после них что-то могло сместиться. Прямой проверки
   «потрогать рукой сейчас» не было — владелец выключил робота.

Проверка, которая различит версии: при включённом роботе взять голову рукой и
попробовать увести её ниже 1674. Если идёт — версия 1.

### 8.2 Поток телеметрии: расхождение в скорости

Два прогона на одном порту дали несопоставимые числа:

- `furo_probe.py`, окно 0.3 с: 172 977 байт, 406 чтений;
- разбор кадров, окно 0.4 с: 147 байт, 7 кадров.

Первое число физически не согласуется со скоростью 115200 бод. Причина
расхождения не установлена. Кроме того, ранее пассивный захват без единой
отправленной команды дал **0 кадров**, а в этих прогонах телеметрия шла
непрерывно. Условие, при котором контроллер начинает стримить, не выяснено.

### 8.3 Адресация записи

`RequestLimit` в декомпиле шлёт на `0xFE`, ответ приходит от `0x2E`,
`SetLimit` шлёт на `0x2F`. Почему так — не установлено. `0x2E` и `0x2F` в
конфигурации ROS — идентификаторы левого и правого колеса.

### 8.4 Что не проверено вообще

- Сохраняется ли `SetLimit` после перезагрузки контроллера.
- Принимает ли контроллер `SetLimit` вообще (кадр ни разу не отправлялся).
- Точный масштаб 20 ед/° (протрактор не использовался, владелец решил
  доверять конфигу).
- Какое значение является геометрической осью робота (5.2).
- Формат команд `ServoPower (0x55)`, ответов на `A4`/`B1`/`B2`, путь
  напряжения батареи, физическая идентификация платы сонаров.

### 8.5 Состояние сети

Робот был выключен владельцем в 15:3x. До выключения SSH работал, порт
освобождался. Причина, по которой робот не переподключился к точке после
перезапуска hostapd, не выяснялась — робот уже был выключен.

## 10. Ближайшие действия, если продолжать

1. При включённом роботе проверить версию 8.1: потянуть голову рукой ниже
   1674.
2. Если версия 1 подтвердится — решить, отправлять ли `SetLimit`
   (`FF FF 2F 0A 03 B1 2B 50 05 EA 06 38 09 61`), предварительно
   сохранив откатный кадр из 2.3. После отправки сразу прочитать лимиты
   обратно тем же запросом из 2.2.
3. Уточнить у владельца, какое показание энкодера соответствует
   геометрической оси робота, и выставить `zero` в трекере по нему.
4. Разобраться с 8.2: почему поток телеметрии то идёт, то нет, и почему
   скорость чтения расходится в 1000 раз.

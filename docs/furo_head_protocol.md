## Подтверждённая команда

Голова FURO-D использует **абсолютную позицию unsigned 16-bit**, а не
знаковую скорость колёс и не относительный инкремент. COM-порт общий с колёсами:
COM3, 115200, 8N1 в исследованной Windows-конфигурации. На Jetson подключение
идёт через **USB–DB9 COM-адаптер**, Linux-алиас из `robot_params.yaml` —
`/dev/tty_motors`. Пины UART Jetson не используются. Для ROS следует использовать
уже открытый порт аппаратного драйвера и его `serial_mutex_`.

```text
FF FF FE 09 83 1E 04 2B PL PH VL VH CHK
```

| Поле | Значение |
| --- | --- |
| Адрес пакета | `FE`, broadcast |
| Длина | `09`, всего пакет 13 байт |
| Инструкция | `83`, Sync Write |
| Начальный регистр | `1E`, позиция |
| Данных на ось | `04` |
| Ось головы | `2B` (43) |
| `PL PH` | абсолютная позиция, uint16 little-endian |
| `VL VH` | скорость, uint16 little-endian |
| `CHK` | `~sum(packet[2:-1]) & 0xFF` |

**Для головы инструкция `83`, а для колёс в текущем ROS-драйвере — `06`.**
Не подставлять `2B` в колёсный пакет скорости с регистром `20`.

Примеры, воспроизведённые оригинальной DLL:

```text
позиция 1900, скорость 10: FF FF FE 09 83 1E 04 2B 6C 07 0A 00 AB
позиция 1800, скорость 10: FF FF FE 09 83 1E 04 2B 08 07 0A 00 0F
позиция 2000, скорость 10: FF FF FE 09 83 1E 04 2B D0 07 0A 00 47
```

Это доказательство формата команды в софте; реальные пределы и направление
на конкретном механизме требуют проверки. Значение 1900 — сохранённая
калибровка DynRobot, не измерение нынешнего центра головы.

Генератор без обращения к оборудованию:

```bash
python scripts/furo_head_packet.py --position 1900 --speed 10
python scripts/furo_head_packet.py --angle 5
```

Для отправки из уже существующего владельца COM-порта достаточно одного
вызова записи **13 бинарных байт**, не ASCII-строки с hex. Например, если
порт уже открыт через pyserial:

```python
packet = bytes.fromhex("FF FF FE 09 83 1E 04 2B 6C 07 0A 00 AB")
written = serial_port.write(packet)
assert written == len(packet)
```

## Откуда это следует в FutureRobot

Основной исследованный набор — `FutureRobot--/FuroSoftware` (именно его
`FutureRobot.FuroManager.exe` указан процессом-источником в COM-логе).
В конфиге выбран `Robot=FuroD1.1`, `ViewManager=True`.

Цепочка из `analysis/il/Robots.il` и `Devices.il`:

1. `FuroD1_1` создаёт `MobilityJoveTech` и
   `ServoActuatorHeadYawByFuroD(mobilityJoveTech)`.
2. `FuroD1_1.SetHeadYaw(degree, degreePerSec)` устанавливает скорость и
   передаёт **минус degree** в `SetPosition`.
3. `ServoActuatorHeadYawByFuroD` содержит `deviceID=0x2B`, `limitID=0x28`,
   пределы угла -35/0/+35°. Калибровку читает как `BodyPoseLimit.waistPitch`.
4. `SetPosition` масштабирует угол через прочитанные min/center/max,
   затем вызывает `MobilityJoveTech.DriveOneAxis(0x2B, position, velocity)`.
5. `DriveOneAxis` строит указанный пакет `83 1E`.

Название **waist / waistPitch** здесь относится к каналу, который FURO-D
использует для поворота головы. Обычный `ServoActuatorHeadYaw` с ID `27`
предназначен для другой конфигурации робота.

Скорость в базовом `ServoActuator.SetVelocity`:
`raw = trunc(1.2 * clamp(deg_per_sec, 0, 120) * 4096 / 240 / 100)`.
Поэтому 50°/с из кнопок страницы дают raw 10. Значение raw 0 софтом
допускается, но его поведение в прошивке не установлено.

Запрос сохранённых лимитов головы:

```text
FF FF FE 04 02 B1 28 22
```

`MobilityJoveTech.GetPositionLimit` ожидает ответ 14 байт с ID `2E`,
длиной `0A`, `B1` по смещению 5 и `28` по смещению 6. Min/center/max
читаются как uint16 LE по смещениям 7, 9, 11. Ответа с лимитами в данном
логе нет. Запрос и парсер подтверждены кодом, ответ оборудования не проверен.

### Сравнение версий

Проверены 9 расположений `FuroSoftware*` в 7 каталогах FutureRobot, включая
`FuroSoftware_original` и `FuroSoftware_2`. У всех формат тела команды головы
совпадает. В **FutureRobot_1** `MathUtil.CalcCheckSum` возвращает сумму
**без инверсии**: для центра получается `54` вместо `AB`. Это отличается
от остальных 8 наборов, DynRobot и всех 429 валидных ответов в логе.
Использовать checksum из `FutureRobot--`, а не копировать эту особенность
`FutureRobot_1`. Причина расхождения и совместимость его с иной прошивкой
не установлены.

Проверка выполнялась через Mono: `analysis/CapturePackets.cs` подписывается
на `MobilityJoveTech.MessageSending`, вызывает методы сборки пакетов и
печатает байты. SerialPort не создаётся. Результаты и SHA256 DLL сохранены
в `analysis/version_packet_checks.json`.

## DynRobot и DynPult

В `DynRobot/config.txt:98` выбран драйвер `FURO`, COM3. Сохранено:

```ini
FURO_HEAD_USE = 1
FURO_ROBOT_HEAD_COEFFICIENT = 8.7266e-4
FURO_HEAD_ZERO = 1900
FURO_MAX_HEAD_ANGLE = 15.0
```

Коэффициент имеет размерность радиан на единицу позиции: примерно
20 единиц на градус. Native-код `dynrobot.exe` независимо подтверждает:

- `0x458F00`: ограничение угла; `raw = trunc(angle_rad / coefficient) + center`.
- `0x4592E0`: сборка `FF FF FE 09 83 1E 04 2B PL PH 0A 00 CHK` и запись
  13 байт через WinAPI WriteFile. Скорость фиксирована: 10.
- `0x458EE0`: обратный пересчёт `(last_commanded_raw - center) * coefficient`.
  Это **последняя отправленная позиция**, а не доказательство получения
  настоящего положения головы из энкодера.

Адреса относятся к скопированному `DynRobot/dynrobot.exe`; полный
дизассемблерный вывод — `analysis/dynrobot.asm`.
Предел ±15° соответствует примерно raw 1600–2200. Знак DynRobot нельзя
автоматически приравнивать к знаку API FutureRobot: последний инвертирует угол.

В обычном режиме DynRobot сравнивает изменение угла с 0.005 рад (~0.286°,
около 6 raw единиц). После отправки устанавливает таймер 4000 мс;
малые последующие изменения могут ждать его истечения. Опциональный режим
`FURO_USE_SMOOTH_HEAD_CONTROL` разбивает движение на шаги до 60 raw единиц
с интервалом более 500 мс. Это найденные программные причины задержек,
но не доказательство механической мёртвой зоны или порога прошивки.

`DynPult/dynpult.ini` и `DynRobot/config.txt` указывают порт дистанционного
управления **5554** (`DIRECT_CONTROL_PORT`); в DynPult включено `head=1`,
`headAxis=2`, `headDeltas=1`. Это уровень DynPult ↔ DynRobot. Сам DynRobot
переводит команды в UART-пакет выше. Сетевой формат и аутентификация DynPult
полностью не восстановлены; для управления из ROS они не нужны.
EXE, INI и руководство пользователя DynPult сохранены целиком.

## Что действительно есть в logs5(1).html

6943 строки событий Windows serial monitor:

- 87 `IRP_MJ_WRITE/DOWN`, все одинаковы: `FF FF 2E 04 03 A0 05 25`.
  Это `MobilityJoveTech.SetEncoderType(5)` — включение режима телеметрии.
  Соответствующие WRITE/UP не надо повторно считать отправками.
- 384 непустых READ/UP, после склейки и разбора **429 кадров по 19 байт**.
  Все имеют вид `FF FF 2E 0F 47 A0 ... CHK`; checksum всех верна,
  пропущенных/лишних байт в объединённом потоке нет.
- Команд `83 1E` головы, команд скорости колёс и запросов калибровки нет.
  Изменение показаний само по себе не доказывает, чем вызвано движение.

Три 32-битных little-endian поля с offset 6, 10, 14:

| Поле | Минимум | Максимум | Статус |
| --- | ---: | ---: | --- |
| 1 | -18 | 15 | колёсный канал |
| 2 | -4150 | 4324 | колёсный канал |
| 3 | 1747 | 1775 | энкодер головы — назначение уточнено владельцем робота |

`MobilityJoveTech.GetEncoderData` явно использует первые два поля для колёс.
После разбора владелец робота уточнил: первые два поля — позиции моторов
колёс, третье — энкодер головы. Это назначение третьего поля подтверждено
владельцем, а не независимо восстановлено по парсеру DLL. В этом логе
голова имеет показания 1747–1775 (размах 28 единиц). Владелец дополнительно
подтвердил, что голова в этой записи **не вращалась**: это колебания показаний
неподвижной головы, а не её рабочий диапазон. Команд движения в записи нет.
`GetPositionData` головы в оригинале ожидает другой формат ответа.
Числа порядка ±2000 из воспоминаний хорошо согласуются со вторым
колёсным каналом.

Для данного 19-байтового кадра `FF FF 2E 0F 47 A0 ... CHK` энкодер головы
находится по смещению **14** от начала кадра, занимает **4 байта LE**.
Для анализа все три поля декодированы как int32; диапазон знака и
разрядность физического датчика головы по этой записи не установлены.
Коэффициент DynRobot относится к задаваемой позиции: применять его к
обратной связи без проверки соответствия шкал нельзя.

Декодированные значения: `analysis/telemetry.csv`.

## Снятие тока и удержания

Сравнение с рабочим колёсным ROS-драйвером: оригинальный
`MobilityJoveTech.DriveDifferential(leftVelocity, leftTime, rightVelocity, rightTime)`
формирует тот же 18-байтовый пакет `FF FF FE 0E 06 20 04 2E ... 2F ... CHK`,
что и `GuideRobotSystem::writeSpeedPacket`: int16 LE скорости и ещё uint16 LE
на каждый слот, одинаковая инвертированная сумма. В DynRobot последние два
байта каждого слота фиксированы `E8 03` (1000), что совпадает с текущим
`motor_accel: 1000`. В FutureRobot аргументы называются `Time`; одной
совместимости байтов недостаточно для доказательства единиц этого поля.
Оригинальный метод кладёт rightVelocity в слот `2E`, leftVelocity — в `2F`;
знаки/перестановка ROS уже определены его конфигурацией и проверены ездой.
Перехват оригинальной DLL для слотов (123, -321) и (0, 0) побайтно совпал
с форматом ROS при дополнительном поле 1000. Артефакты:
`analysis/CaptureWheels.cs`, `analysis/wheel_packets.txt`.

Таким образом, совместимость **команды скорости** подтверждена.
Это не подтверждает автоматически поддержку команды ServoPower формата `55`:
в той же DLL есть вспомогательные методы другого формата.

В текущем `guide_robot_hardware/src/guide_robot_system.cpp` **нет отдельной
команды отключения силовой части/torque-off**. Все записи в COM — запрос
телеметрии и `writeSpeedPacket`. При deactivate, ошибке и срабатывании
watchdog отправляется нулевая скорость через тот же пакет `06 20`.
Нулевая скорость не является явно реализованной командой снятия тока.

Владелец наблюдает, что после подачи питания моторы свободны, а после запуска
ROS появляется удержание. В `on_activate` отдельной команды enable нет;
в рабочем цикле начинают идти команды скорости, в том числе нулевой.
Гипотеза: включение силовой части происходит при приёме первой команды
скорости. Это ещё надо отделить экспериментом от эффекта открытия COM-порта
и запроса телеметрии. Поведение подготовленного capture-скрипта при холодном
старте контроллера на оборудовании пока не проверялось.

В оригинальной DLL найден `MobilityJoveTech.ServoPower(id, mode)`.
`FormFuroSTester.checkBoxWaistEnable_CheckedChanged` вызывает для канала
головы `ServoPower(3, 0)` при выключении и `ServoPower(3, 2)` при включении.
Перехват оригинальной DLL без оборудования даёт:

```text
ServoPower(3, 0): 55 03 83 00 00 00 00
ServoPower(3, 2): 55 03 83 08 00 00 00
```

Здесь `3` — номер канала API ServoPower; это не позиционный адрес `2B`.
**Это другой формат, начинающийся с `55`, без Dynamixel checksum.**
Наличие метода и привязка к выключателю подтверждены кодом, но приём этой
команды установленной прошивкой FURO-D и реальное снятие тока не проверены.
В ROS и capture-скрипт она не добавлена. Перехватчик и байты сохранены
в `analysis/CaptureServoPower.cs` и `analysis/servo_power_packets.txt`.

## Снятие крайних положений вручную на Jetson

Подготовлен самостоятельный `scripts/furo_head_capture.py`: Python 3,
стандартная библиотека Linux, без ROS, pyserial и привязки к модели Jetson.
Запускать **до ROS-стека** на свободном USB–DB9 COM-порту. Скрипт открывает
`/dev/tty_motors` на 115200 8N1 и каждые 200 мс отправляет только
`FF FF 2E 04 03 A0 05 25`. Команд движения, изменения усилений и отключения
удержания он не отправляет. Порт закрывается при выходе; блокировка
`TIOCEXCL` на время записи препятствует новым обычным открытиям порта.
Стек во время записи не запускать.

На месте выгрузим файл и запустим на **хосте Jetson**, без контейнера:

```bash
# На ноутбуке; 10.42.0.1 — адрес из scripts/jetson_hotspot.sh,
# фактический адрес подключения уточним на месте.
scp scripts/furo_head_capture.py jetson@10.42.0.1:~/furo_head_capture.py
ssh -t jetson@10.42.0.1

# На Jetson, до старта стека:
python3 ~/furo_head_capture.py --output ~/head-capture-$(date +%Y%m%d-%H%M%S)
```

При другой раскладке USB можно явно задать `--port /dev/ttyUSB0`, предварительно
проверив, что это адаптер контроллера моторов. По умолчанию используется
проектный алиас `/dev/tty_motors`, а не первый попавшийся USB-порт.

Порядок работы:

1. Скрипт непрерывно показывает текущий энкодер головы, общий min/max и число кадров.
2. Повернуть голову вручную к левому пределу, удерживать около секунды,
   ввести **`l` + Enter**.
3. Повернуть к правому пределу, удерживать секунду, **`r` + Enter**.
4. По желанию выставить голову прямо, удерживать секунду, **`c` + Enter**.
5. **`q` + Enter** или Ctrl+C завершает запись и освобождает порт.

Отметки можно повторять: последняя заменяет прежнюю. Для каждой сохраняется
медиана последней секунды, min/max, размах и число кадров; устаревшее или
незаполненное окно не принимается. Размах окна виден сразу, чтобы заметить,
если голова ещё двигалась. Время окна можно изменить через `--window`.

Каталог результатов содержит:

- `rx.bin` — все принятые байты, включая повреждённые/неопознанные;
- `samples.csv` — время приёма, оба колёсных счётчика, энкодер головы и hex каждого
  валидного кадра;
- `summary.json` — отметки left/right/center, число ошибок checksum,
  общий наблюдавшийся диапазон и итоговые пределы по медианам отметок.

Промежуточная `summary.json` сохраняется при каждой отметке, итоговая — и при
Ctrl+C/ошибке. Отсутствие ответов более 5 секунд завершает запись с ошибкой.
Если оба предела не отмечены, скрипт явно сообщает о незавершённой калибровке.
Полусумма пределов выводится как `midpoint`: это вычисленная середина,
а не автоматически подтверждённое положение головы прямо. Реальный центр
лучше отдельно отметить через `c`. Градусы по этому опыту без известного
физического угла вычислить нельзя.

Для неинтерактивной записи можно указать `--duration 30`; отметок пределов
в таком режиме не будет. Файл подготовлен локально; на робота ещё не выгружался.
Для начальной проверки открытия USB–DB9 COM без передачи байтов добавлен
`--passive`, например `--passive --duration 3`. При отсутствии телеметрии
он сохранит пустую запись с ошибкой; это не означает, что была отправлена команда.
Порядок первого сеанса и ограничение разрешённого пакета описаны
в [плане проверки на роботе](furo_on_robot_check.md).

Проверка без оборудования:

```bash
python3 -m unittest discover -s scripts -p test_furo_head_capture.py -v
```

Тесты проверяют повреждённые/разорванные пакеты, свежесть отметок, полный
сеанс через псевдо-COM, интерактивное снятие обоих пределов, таймаут и
освобождение порта. На исходном COM-логе новый декодер восстановил все
429 кадров без ошибок и потерь.

## Что осталось проверить на роботе

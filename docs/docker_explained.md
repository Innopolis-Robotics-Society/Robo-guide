# Docker: теория и практика на примере Robo-guide

Это руководство объясняет, как устроен Docker, где находятся данные и что происходит
при запуске, остановке, пересоздании и сохранении контейнера. Примеры Robo-guide
соответствуют текущему [compose.yaml](../compose.yaml).

Команды ниже — примеры для самостоятельного выполнения. Команды проекта выполняются
**на хосте из корня Robo-guide**, если явно не указано «внутри контейнера».

## 1. Зачем нужен Docker

Для запуска робота нужны ROS 2, Python, системные библиотеки и зависимости пакетов.
Если устанавливать всё прямо на компьютер, версии разных проектов могут конфликтовать.
Docker позволяет подготовить окружение и запускать программы внутри него.

При этом программа использует реальные CPU, память, диски и устройства компьютера.
Контейнеризация помогает управлять окружением, но не заменяет настройку оборудования.

**Хост** — компьютер, на котором работает Docker. В этом проекте хостом может быть
Jetson или рабочая станция с Ubuntu.

## 2. Контейнер и виртуальная машина

Виртуальная машина запускает гостевую ОС со своим ядром. Linux-контейнер использует
ядро Linux-хоста, а файлы программ и библиотек получает из образа.

Например, образ с Ubuntu содержит её пользовательское окружение: `bash`, библиотеки,
пакетный менеджер. Он не запускает отдельное ядро Ubuntu.

Изоляцию обеспечивают механизмы Linux: namespaces разделяют видимость процессов,
сети и других ресурсов, а cgroups позволяют учитывать и ограничивать ресурсы.
На macOS и Windows Docker Desktop обычно запускает Linux-контейнеры внутри Linux-VM.

Источник: [что такое контейнер](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/).

## 3. Образ, контейнер, Dockerfile и Compose

| Понятие | Что это | Пример |
|---|---|---|
| Образ, image | Подготовленная файловая система и настройки запуска | `fabook/iros:jetson` |
| Контейнер, container | Экземпляр образа со своими изменениями и состоянием | `robo-guide-jetson-1` |
| Dockerfile | Инструкции для сборки образа | `.docker/Dockerfile.jetson` |
| Compose-файл | Описание сервисов и настроек их контейнеров | `compose.yaml` |
| Сервис Compose | Именованное описание того, что запускать | `jetson` |
| Registry | Сервер для хранения и распространения образов | Docker Hub |
| Bind mount | Подключение конкретного пути хоста в контейнер | `./install:/home/fabian/ros2_ws/install` |
| Volume | Хранилище, которым управляет Docker | `db-data:/var/lib/postgresql/data` |

Связь между ними:

```text
Dockerfile + файлы для сборки
            |
       docker build
            v
           образ <-------- docker pull -------- registry
            |  ---------- docker push --------> registry
            |
     настройки из compose.yaml
            |
     docker compose up
            v
         контейнер <------ подключённые каталоги хоста
            |
       процессы приложения
```

Dockerfile отвечает на вопрос «что подготовить внутри образа?», а Compose-файл —
«как запускать контейнеры в этом окружении?».

Источник: [Docker Compose](https://docs.docker.com/reference/cli/docker/compose/).

## 4. Как работает сам Docker

Команда `docker` — клиент. Он отправляет запрос Docker Engine, который управляет
образами, контейнерами, сетями и хранилищами. Сборку образов обычно выполняет BuildKit.

```text
Ты вводишь команду
        |
        v
docker CLI / Docker Compose
        |
        v
Docker Engine
        |
        v
Создание контейнера и запуск процесса
```

Поэтому «не удаётся подключиться к Docker daemon» означает проблему подключения
к Engine или его доступности, а не ошибку ROS внутри контейнера. Клиент также может
быть настроен на удалённый Engine: смотри `docker context show`.

Источник: [Docker Engine](https://docs.docker.com/engine/).

## 5. Как устроен образ

Образ содержит слои файловой системы и конфигурацию: пользователя, рабочий каталог,
команду запуска, значения переменных окружения по умолчанию.

```text
Настройки запуска
----------------------------
Дополнительные зависимости
ROS 2 и его пакеты
Базовое окружение Ubuntu
```

Слои можно повторно использовать между образами. Сам созданный образ неизменяем:
сборка обновлённой версии создаёт новый образ.

В имени `fabook/iros:jetson`:

- `fabook` — пространство имён в registry;
- `iros` — репозиторий образов;
- `jetson` — тег.

**Тег — перемещаемая метка.** Сегодня он может указывать на один образ, завтра —
на другой. `latest` — обычный тег, а не гарантия самой новой версии.

Image ID идентифицирует локальный образ. Registry digest вида `sha256:…` фиксирует
конкретное содержимое опубликованного манифеста. Тег удобен для работы, digest —
для точного выбора версии.

Источник: [что такое образ](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/).

## 6. Что появляется при создании контейнера

Docker добавляет поверх образа отдельный **слой записи** контейнера.

```text
                   Один образ
                 /            \
         Контейнер A        Контейнер B
         Слой записи A      Слой записи B
```

Если установить пакет внутри A, он появится в слое A. Образ и контейнер B от этого
не изменятся. Новый контейнер C из исходного образа тоже не получит этот пакет.

При остановке контейнера его слой записи сохраняется. При удалении контейнера —
теряется. Подключённые внешние хранилища имеют отдельный жизненный цикл.

Это объясняет частую ситуацию: «Вчера пакет был установлен, а после нового запуска
его нет». Возможно, вчера ты установил его в контейнере, а сегодня создал другой.

Источник: [слои образа](https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/).

## 7. Dockerfile: как описать окружение

Учебный пример, независимый от Robo-guide:

```dockerfile
FROM ubuntu:22.04

RUN apt-get update \
    && apt-get install -y --no-install-recommends python3 \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY hello.py /app/hello.py
ENV PYTHONUNBUFFERED=1
CMD ["python3", "/app/hello.py"]
```

Рядом с этим Dockerfile должен находиться `hello.py`:

```python
print("Привет из контейнера")
```

| Инструкция | Что задаёт |
|---|---|
| `FROM` | Базовый образ |
| `RUN` | Команду, выполняемую **при сборке** |
| `COPY` | Копирование файлов из контекста сборки |
| `WORKDIR` | Рабочий каталог |
| `USER` | Пользователя для следующих инструкций и запуска |
| `ARG` | Параметр сборки; автоматически в окружение запуска не переносится |
| `ENV` | Переменную окружения по умолчанию |
| `CMD` | Команду или аргументы по умолчанию **при запуске** |
| `ENTRYPOINT` | Основную команду, к которой обычно добавляются аргументы `CMD` |
| `EXPOSE` | Метаданные о порте; сам по себе порт на хосте не открывает |

`RUN` устанавливает Python во время сборки. `CMD` запускает программу уже в контейнере.
Командой запуска можно переопределить `CMD`. `ENTRYPOINT` переопределяется отдельно.

Источник: [инструкции Dockerfile](https://docs.docker.com/reference/dockerfile/).

## 8. Сборка, контекст и кеш

Для учебного примера из предыдущего раздела:

```bash
docker build -t docker-lesson:v1 .
docker run --rm docker-lesson:v1
```

Последняя точка в `build` — **контекст сборки**, здесь текущий каталог. Dockerfile
получает файлы для `COPY` из этого контекста.

Для Jetson в Robo-guide предусмотрена команда:

```bash
docker build -f .docker/Dockerfile.jetson -t fabook/iros:jetson .
```

Здесь `-f` выбирает Dockerfile, `-t` задаёт тег результата, а `.` выбирает корень
репозитория как контекст. Наличие Dockerfile в подкаталоге не меняет контекст.

[.dockerignore](../.dockerignore) исключает из контекста, например, `.git`, `.env`
и результаты сборки ROS. `.gitignore` относится к Git и не заменяет `.dockerignore`.

Источник: [контекст сборки](https://docs.docker.com/build/concepts/context/).

Docker может использовать кеш предыдущих шагов. Если изменился файл, который копирует
`COPY`, соответствующий шаг и зависимые от него шаги выполняются заново.
В [Dockerfile.jetson](../.docker/Dockerfile.jetson) скрипты зависимостей копируются
по отдельности: это позволяет сохранять кеш более ранних этапов.

**`docker build` не обновляет уже созданный контейнер.** Для применения нового образа
нужно создать контейнер из него или пересоздать существующий.

Источник: [кеш сборки](https://docs.docker.com/build/cache/invalidation/).

## 9. Жизненный цикл: создать, запустить, остановить, удалить

```text
Образ
  |
  | create
  v
Созданный контейнер -- start --> Работающий контейнер
                              <-- stop / завершение процесса

Созданный или остановленный контейнер -- rm --> Удалён
```

`docker run` объединяет создание нового контейнера и его запуск.
`docker start` запускает уже существующий остановленный контейнер.
`docker exec` создаёт дополнительный процесс в работающем контейнере.

Контейнер работает, пока жив его главный процесс, PID 1. Если команда контейнера —
скрипт, который завершился, контейнер тоже остановится. Флаг `-d` только отсоединяет
терминал: он не удерживает завершившуюся программу в работе.

```bash
# Новый контейнер с интерактивным bash, удаляется после выхода
docker run --rm -it ubuntu:22.04 bash

# Список работающих контейнеров
docker ps

# Включая остановленные контейнеры
docker ps -a
```

Флаги: `-i` оставляет stdin открытым, `-t` выделяет псевдотерминал,
`--rm` удаляет контейнер после завершения.

Источник: [запуск контейнеров](https://docs.docker.com/engine/containers/run/).

## 10. Где хранятся данные

### 10.1. Слой записи контейнера

Если путь не подключён извне, изменение обычно записывается в слой контейнера.
Пример: установка системного пакета в `/usr`.

### 10.2. Bind mount: конкретный каталог хоста

В Robo-guide используется:

```yaml
volumes:
  - .:/home/fabian/ros2_ws/src:rw
  - ./build:/home/fabian/ros2_ws/build:rw
  - ./install:/home/fabian/ros2_ws/install:rw
  - ./log:/home/fabian/ros2_ws/log:rw
```

Слева — путь хоста, справа — путь внутри контейнера. `rw` разрешает чтение и запись;
`ro` разрешает только чтение.

```text
Хост Robo-guide/install/
          ↕ одни и те же файлы
Контейнер /home/fabian/ros2_ws/install/
```

Изменения файлов через любой из этих путей видны с другой стороны. Bind mount
**закрывает собой** файлы образа в точке подключения: они не удалены, но скрыты
под содержимым каталога хоста.

Хотя настройка называется `volumes:`, записи с путями `.` и `./install` — это
именно bind mounts, а не именованные Docker volumes.

Источник: [bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).

### 10.3. Именованный volume

Пример для базы данных, не часть текущего Compose Robo-guide:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD:?Set DB_PASSWORD}
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

Здесь `db-data` — имя хранилища Docker. Оно существует отдельно от контейнера.
Точное расположение файлов на хосте обычно не нужно указывать приложению.

Источник: [Docker volumes](https://docs.docker.com/engine/storage/volumes/).

### 10.4. tmpfs и сохранность данных

`tmpfs` подходит для временных файлов: данные не предназначены для постоянного
хранения и исчезают после остановки или перезапуска контейнера.

| Где записан файл | После остановки | После удаления контейнера | Входит в `docker commit` |
|---|---|---|---|
| Слой записи | Сохраняется | Теряется | Да |
| Bind mount | Сохраняется на хосте | Сохраняется на хосте | Нет |
| Именованный volume | Сохраняется | Сохраняется, пока отдельно не удалён volume | Нет |
| tmpfs | Теряется | Теряется | Нет |

Источник: [хранение данных](https://docs.docker.com/engine/storage/).

## 11. Docker Compose и настройки Robo-guide

Compose позволяет записать параметры запуска в YAML, чтобы не повторять длинный
`docker run` с устройствами, переменными и подключениями каталогов.

Упрощённая учебная версия сервиса:

```yaml
services:
  jetson:
    image: fabook/iros:jetson
    working_dir: /home/fabian/ros2_ws
    volumes:
      - .:/home/fabian/ros2_ws/src
    stdin_open: true
    tty: true
    command: ["bash"]
```

Реальный [compose.yaml](../compose.yaml) дополнительно задаёт доступ к устройствам,
NVIDIA runtime, звук, графику, окружение ROS и команды подготовки каталогов.

В нём `x-common: &common-setup` задаёт общий блок YAML, а `<<: *common-setup`
подставляет его в сервис. Если сервис задаёт собственный список `volumes`, этот список
заменяет общий целиком. Поэтому у `jetson` подключения PulseAudio повторены.

Корневой Compose описывает несколько сервисов для разных вариантов оборудования.
Команда `docker compose up` без имени сервиса попытается запустить их все. Для Jetson
выбирай `docker compose up -d jetson`.

**В текущем проекте `up` запускает окружение с `bash`.** ROS-стек отдельно запускает
[Jetson launcher](../scripts/jetson-launcher/README.md) через `docker exec`.
Работающий контейнер ещё не означает, что все ROS-узлы запущены.

## 12. `up`, `run` и `exec`: три разных действия

| Команда | Новый контейнер? | Основной смысл |
|---|---|---|
| `docker compose up -d jetson` | Если нужен: создаёт или пересоздаёт | Запуск основного сервиса в фоне |
| `docker compose run --rm jetson bash` | Да, отдельный | Разовая задача по настройкам сервиса |
| `docker compose exec jetson bash` | Нет | Дополнительный процесс в работающем сервисе |

### `up`: основной контейнер сервиса

```bash
docker compose up -d jetson
```

Повторный `up` не обязательно создаёт новый контейнер: Compose может оставить
работающий без изменений или запустить остановленный. При изменении образа или
конфигурации Compose обычно пересоздаёт контейнер.

Без `-d` команда показывает вывод контейнеров в терминале. Остановка такого `up`
через Ctrl+C останавливает запущенные им контейнеры.

Источник: [`docker compose up`](https://docs.docker.com/reference/cli/docker/compose/up/).

### `run`: отдельный контейнер для задачи

```bash
docker compose run --rm jetson bash
```

Он использует образ, окружение и mounts сервиса, но не входит в основной контейнер.
Имя обычно имеет вид `robo-guide-jetson-run-…`. При `--rm` после выхода контейнер
удаляется вместе со своим слоем записи.

Переданная команда `bash` заменяет `command` сервиса. В Robo-guide так пропускаются
подготовительные действия из `command`; ENTRYPOINT образа при этом не заменяется.

`run` по умолчанию не публикует `ports` сервиса. Для этого есть `--service-ports`.
У Robo-guide используется host-сеть, поэтому это отличие здесь несущественно.
Зависимости сервиса могут запускаться автоматически; `--no-deps` отключает это.

Источник: [`docker compose run`](https://docs.docker.com/reference/cli/docker/compose/run/).

### `exec`: работа в существующем контейнере

```bash
docker compose exec jetson bash
```

Изменения в обычных системных каталогах относятся к основному контейнеру.
Выход из этого дополнительного `bash` обычно не останавливает контейнер,
поскольку его главный процесс продолжает работать.

Источник: [`docker compose exec`](https://docs.docker.com/reference/cli/docker/compose/exec/).

### Названия нельзя смешивать

```bash
# Compose получает имя СЕРВИСА
docker compose exec jetson bash

# Обычный Docker получает имя или ID КОНТЕЙНЕРА
docker exec -it robo-guide-jetson-1 bash

# docker run получает имя ОБРАЗА
docker run --rm -it fabook/iros:jetson bash
```

Последняя команда не читает Compose: устройства, NVIDIA runtime и mounts из
`compose.yaml` автоматически к ней не добавятся.

## 13. Остановка, перезапуск и пересоздание

| Команда | Что происходит |
|---|---|
| `docker compose stop jetson` | Останавливает контейнер, сохраняет его слой записи |
| `docker compose start jetson` | Запускает уже созданный контейнер |
| `docker compose restart jetson` | Перезапускает тот же контейнер |
| `docker compose up -d --force-recreate jetson` | Заменяет основной контейнер новым |
| `docker compose down` | Удаляет контейнеры проекта и его обычные Compose-сети |
| `docker compose down -v` | Дополнительно удаляет объявленные именованные и подключённые анонимные volumes; external volumes не удаляются |

`restart` не подхватывает новый образ, новые переменные окружения или изменённые
mounts. Эти параметры определяются при создании контейнера.

`down` по умолчанию не удаляет образы и именованные volumes. Bind mounts остаются
на хосте даже при `down -v`, но изменения во внутреннем слое контейнера теряются
при его удалении или пересоздании.

**Особенность этого робота:** перед остановкой или пересозданием контейнера сначала
штатно останови ROS-стек через интерфейс launcher. В проекте описано, что принудительное
завершение драйвера может помешать отправке стоп-пакета моторам. Это относится также
к `up`, если он собирается пересоздать контейнер. Подробности:
[безопасность перезапуска](../scripts/jetson-launcher/README.md#безопасность-перезапуска).

Источники: [`restart`](https://docs.docker.com/reference/cli/docker/compose/restart/),
[`down`](https://docs.docker.com/reference/cli/docker/compose/down/).

## 14. Переменные окружения и `.env`

Переменная окружения — строковое значение, которое процесс получает при запуске.
В Robo-guide примером служит `SELECTEL_AIG_KEY`.

Нужно различать:

- `ENV` в образе — значение по умолчанию;
- окружение shell хоста — переменные терминала, из которого запускаешь Compose;
- `.env` — источник значений для Compose;
- `environment` и `env_file` сервиса — способы передать значения в контейнер.

Наличие произвольной переменной в `.env` само по себе не передаёт её в контейнер.
В текущем Compose явно указано:

```yaml
environment:
  - SELECTEL_AIG_KEY
```

Поэтому значение берётся из окружения хоста или `.env`. Если значение не определено,
Compose не передаст эту переменную. Пустое значение и отсутствующая переменная —
разные состояния, хотя приложение может считать оба случая отсутствием ключа.

Для этого проекта экспортированное значение в shell имеет приоритет над `.env`.
Окружение, заданное Compose, переопределяет соответствующее значение `ENV` образа.
`docker compose run -e NAME=value` позволяет переопределить значение для разового запуска.

Изменение `.env` не меняет окружение уже работающих процессов: нужен новый контейнер.
`export` внутри открытого `bash` влияет на этот shell и его будущие дочерние процессы,
но не на другие процессы и не на образ.

Источник: [приоритет переменных](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/).

## 15. Сеть: адреса и порты

В обычной Compose bridge-сети контейнеры имеют отдельные сетевые пространства
и могут обращаться друг к другу по имени сервиса, например `db:5432`.

`localhost` внутри контейнера обозначает сам этот контейнер. Для доступа с хоста
порт публикуют:

```yaml
ports:
  - "127.0.0.1:8080:8000"
```

Здесь порт `8080` хоста направляется на `8000` контейнера. Приложение внутри
контейнера обычно должно слушать `0.0.0.0:8000`, чтобы принимать такие подключения.
Привязка хостовой стороны к `127.0.0.1` ограничивает доступ локальным компьютером.

В Robo-guide задано:

```yaml
network_mode: host
```

На Linux контейнер использует сетевое пространство хоста. `localhost` общий,
отдельное пробрасывание `ports` не требуется. Два процесса, которым нужен один
и тот же адрес и порт, могут конфликтовать даже в разных контейнерах.

Host-сеть удобна для ROS 2, но сетевой конфликт нужно искать среди процессов
как хоста, так и контейнера.

Источник: [сеть Docker](https://docs.docker.com/engine/network/).

## 16. Права, устройства, GPU и архитектура

Права файлов Linux определяются UID и GID, а не только именами пользователей.
Если контейнер пишет в bind mount, созданные файлы имеют числового владельца
процесса контейнера. Поэтому файл от `root` в контейнере может оказаться недоступен
обычному пользователю хоста.

В Robo-guide Dockerfile задаёт пользователя `fabian`, а Compose добавляет группы
для видео, аудио и последовательных устройств. Доступ к Docker Engine обычно
даёт широкие возможности управления хостом.

`privileged: true` предоставляет контейнеру расширенные права.
Подключение `/dev` открывает пути устройств хоста. Это выбранная конфигурация
робота, а не свойство всех контейнеров Docker.

Источник: [безопасность Docker Engine](https://docs.docker.com/engine/security/).

Jetson использует ARM64, обычная рабочая станция часто использует AMD64/x86_64.
Образ для одной архитектуры не становится образом для другой после переименования
тега. Для запуска чужой архитектуры может потребоваться эмуляция.

Для GPU дополнительно нужны совместимые драйверы и runtime хоста. В текущем
[Dockerfile.jetson](../.docker/Dockerfile.jetson) базовый образ привязан к версии
L4T, а в Compose указан `runtime: nvidia`. Нужно согласовать окружение образа
с JetPack устройства.

Переносимость Docker означает перенос подготовленного окружения при совместимых
архитектуре, ядре, драйверах и ресурсах. Она не устраняет эти зависимости.

Источник: [образы для разных платформ](https://docs.docker.com/build/building/multi-platform/).

## 17. `docker commit`: что сохраняет твоя команда

```bash
docker commit \
  --change 'ENV SELECTEL_AIG_KEY=' \
  robo-guide-jetson-1 \
  fabook/iros:jetson
```

Она создаёт локальный образ из изменений и конфигурации **конкретного** контейнера
`robo-guide-jetson-1`, выставляет ключ в пустую строку в конфигурации результата
и перемещает локальный тег `fabook/iros:jetson` на новый образ.

`commit` не сохраняет RAM и работающие процессы, данные mounts, настройки оборудования
хоста или Compose-файл. При обычном выполнении контейнер кратко приостанавливается.
Результат также не отправляется автоматически в registry.

**Обнуление `ENV` не гарантирует удаление всех копий секрета**: ключ мог попасть
в файлы, историю shell или нижние слои. Это изменение значения в конфигурации
нового образа, а не очистка всего его содержимого.

Изменения уже работающего контейнера этой командой не применяются обратно к нему.
`commit` полезен как временный снимок для отладки, но Dockerfile лучше описывает
воспроизводимую установку зависимостей.

Источник: [`docker commit`](https://docs.docker.com/reference/cli/docker/container/commit/).

### Как могла возникнуть ошибка

По одной приведённой команде нельзя доказать, что произошло именно у тебя.
Вот сценарии, которые объясняются устройством Docker и настройками проекта:

| Действия | Результат |
|---|---|
| Установил пакет через `compose run`, затем сделал `commit robo-guide-jetson-1` | Сохранён другой контейнер; пакет из разового контейнера не попал в образ |
| Установил пакет через `compose run --rm`, вышел | Разовый контейнер удалён; изменения его системных каталогов потеряны |
| Собрал ROS в подключённом `install`, затем сделал `commit` | Результат остался на хосте, но не вошёл в образ |
| Сделал `commit` и продолжил пользоваться старым контейнером | Старый контейнер сам не переключился на новый образ |
| Очистил ключ в образе, но Compose передаёт ключ из `.env` | Новый контейнер получает значение из Compose |

Пример с двумя контейнерами:

```text
fabook/iros:jetson
    |
    +-- up  --> robo-guide-jetson-1
    |           пакет НЕ установлен
    |
    +-- run --> robo-guide-jetson-run-…
                пакет установлен здесь

commit robo-guide-jetson-1
    |
    v
Новый образ без пакета из разового контейнера
```

Для временного снимка удобнее отдельный тег, чтобы не терять понятную ссылку
на исходный образ:

```bash
docker commit \
  --change 'ENV SELECTEL_AIG_KEY=' \
  robo-guide-jetson-1 \
  fabook/iros:jetson-debug
```

Перед этим проверяют, какой контейнер действительно содержит нужные изменения.

## 18. Как передавать образ на другой компьютер

Через registry:

```bash
# На компьютере, где образ подготовлен; требуется доступ к репозиторию
docker push fabook/iros:jetson-debug

# На другом компьютере
docker pull fabook/iros:jetson-debug
```

Для передачи файлом:

```bash
# Создать архив образа
docker save -o iros-jetson-debug.tar fabook/iros:jetson-debug

# После передачи архива на другой компьютер
docker load -i iros-jetson-debug.tar
```

`save/load` переносят образ, но не bind mounts, volumes или состояние процессов.
Каталоги проекта и данные нужно передавать отдельно.

`docker export` выгружает файловую систему контейнера без полной структуры образа
и его конфигурации. Для переноса образа обычно нужны именно `save/load`.

Источники: [`save`](https://docs.docker.com/reference/cli/docker/image/save/),
[`load`](https://docs.docker.com/reference/cli/docker/image/load/),
[`export`](https://docs.docker.com/reference/cli/docker/container/export/).

## 19. Рабочий процесс в Robo-guide

### Запустить окружение и открыть shell

На Jetson из корня проекта, когда запуск сервиса уместен:

```bash
docker compose up -d jetson
docker compose exec jetson bash
```

Если сервис уже работает, достаточно `exec`.

### Собрать ROS-пакеты

Внутри контейнера:

```bash
cd /home/fabian/ros2_ws
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

`source` меняет окружение текущего shell. В другом shell окружение нужно подготовить
снова. `exec … bash` может читать `.bashrc`, но произвольный `docker exec … <команда>`
не обязан это делать.

Сборка пишет в `build`, `install`, `log`, подключённые с хоста. Поэтому эти файлы
останутся после удаления контейнера. При смене архитектуры или несовместимого
окружения старые результаты сборки могут потребовать очистки и пересборки.

### Добавить постоянную зависимость

1. Записать установку в соответствующий скрипт `.docker/common/` или Dockerfile.
2. Собрать новый образ нужной платформы.
3. Штатно остановить ROS-стек через launcher.
4. Пересоздать основной контейнер.
5. Запустить стек через launcher и проверить его состояние.

Шаг пересоздания:

```bash
docker compose up -d --force-recreate jetson
```

### Изменить только код проекта

Код уже подключён через bind mount: правки видны в контейнере без пересборки образа.
Но это не означает, что работающая программа автоматически их применит.
Для C++ нужна компиляция; для Python и конфигурации обычно нужен перезапуск
соответствующего процесса, а иногда и повторная сборка пакета.

## 20. Как разобраться в проблеме

Начни с определения объекта: проблема относится к образу, конкретному контейнеру,
файлам хоста или процессу ROS?

```bash
# Локальные образы
docker image ls

# Все контейнеры, включая завершившиеся от compose run
docker ps -a

# Контейнеры текущего Compose-проекта
docker compose ps -a

# Запущенный Compose-проект и используемые им файлы
docker compose ls

# Показать конфигурацию после подстановок
docker compose config

# Логи основного процесса контейнера
docker compose logs --tail=100 jetson

# Изменения в файловой системе контейнера вне mounts
docker diff robo-guide-jetson-1
```

`docker compose config` может вывести ключи из окружения: не публикуй его результат
без проверки. В Robo-guide ROS запускается отдельным процессом через launcher,
поэтому `compose logs` может не содержать его вывод. По текущей документации
launcher пишет его в `/tmp/stack.log` внутри контейнера:

```bash
docker exec robo-guide-jetson-1 tail -n 100 /tmp/stack.log
```

Проверить, какой образ использует контейнер и куда направлены mounts:

```bash
docker inspect --format '{{.Image}}' robo-guide-jetson-1
docker image inspect --format '{{.Id}}' fabook/iros:jetson
docker inspect --format '{{json .Mounts}}' robo-guide-jetson-1
```

Если первые два ID различаются, контейнер создан из другого образа, чем тот,
на который сейчас указывает тег.

Проверить наличие ключа, не печатая его значение:

```bash
docker compose exec jetson bash -c \
  'if [ -n "$SELECTEL_AIG_KEY" ]; then echo "Ключ непустой"; else echo "Ключ отсутствует или пустой"; fi'
```

## 21. Шпаргалка выбора команды

| Что нужно | Что использовать |
|---|---|
| Подготовить окружение с зависимостями | `docker build` |
| Получить опубликованный образ | `docker pull` |
| Запустить основной сервис | `docker compose up -d jetson` |
| Открыть shell в основном работающем сервисе | `docker compose exec jetson bash` |
| Выполнить задачу в отдельном контейнере | `docker compose run --rm jetson <команда>` |
| Применить новый образ или окружение | Пересоздание через `up`, при необходимости `--force-recreate` |
| Временно сохранить изменения конкретного контейнера | `docker commit <контейнер> <образ:тег>` |
| Сохранить зависимость воспроизводимо | Изменить Dockerfile или скрипт сборки |
| Передать образ архивом | `docker save` / `docker load` |
| Сохранить данные при замене контейнера | Bind mount или volume |

Перед действием полезно ответить на три вопроса: **из какого образа создан контейнер,
в каком контейнере ты работаешь и куда физически записываются файлы**.
